## 3. 重箱の隅をつつく敵対的検証（限界条件と運用上の留意点）

リリースを阻害する不具合ではないが、本アプリケーションの設計アーキテクチャ・動作仕様の境界値（Edge Cases）に関して以下の定量的特性を浮き彫りにした。

### 3.1 極めて大容量なデータ（数万件規模）における初回ロードコスト
- **観測**: 
  仕様書 5.3 に定められた保存方式に基づき、`IndexedDbAdapter.loadAll()` はアプリ起動時および変更時にストアの全エンティティをメモリへ一括ロードする。
- **実測評価**: 
  性能目標（案件20件、実施回100件、区間2,000件）の実測値は **35ms未満**（Chromium実測）であり、仕様目標（1000ms）を大幅にクリアしている。ただし、数年以上の運用で作業区間が5万件を超えた場合、JavaScriptのガベージコレクションおよびDOM構築に伴い、初期描画時に数100msのメインスレッドブロッキングが発生しうる。
- **対応方針**: 
  1端末・1管理者運用という前提要件（仕様書 3.1）において、十分なパフォーマンス余裕を確認済み。将来の拡張時のみインデックスキーによる部分ロード化を検討すればよい。

### 3.2 夏時間のない地域（日本）前提とタイムゾーン移動時の影響
- **観測**: 
  `datetime.js` はローカル時刻＋オフセット（例: `+09:00`）でISO 8601文字列を記録する。
- **実測評価**: 
  夏時間（DST）が存在しない日本（JST）での利用を前提（仕様書 8.4.8 / レビュー指摘 SOL-1）とし、オフセット値が明確に記録されるため、日を跨ぐ区間や深夜作業もミリ秒精度で正しく差分計算される。海外等へ端末を持ち込んでタイムゾーンを変更した場合もエポックミリ秒（`parseIso`）ベースで正しく比較・計算される。

### 3.3 ストレージ容量超過（`QuotaExceededError`）時の挙動
- **観測**: 
  ブラウザのストレージ制限やディスク満杯により IndexedDB の書き込みが拒否された場合。
- **実測評価**: 
  `IndexedDbAdapter` が `StorageError`（種別: `QUOTA_EXCEEDED`）を発生させ、トランザクションは完全にロールバックされる。UI上のステータスバー・エラー通知により保存失敗が明確に伝えられ、データ破壊・部分書き込みは発生しない。

### 6.3 F12-01 の再現結果

隔離したメモリ永続化環境で、前後空白付きの値を含む全件 JSON を `validateImport()` に通し、その後に通常アクション相当の検索・重複検査を実行した。

```json
{
  "importAccepted": true,
  "importErrors": [],
  "activeTemplateFoundAfterImport": false,
  "normalizedDuplicateRejected": false,
  "duplicateErrors": []
}
```

インポートの構文・参照整合性が通ることと、インポート後の業務操作が成立することは同義ではない。本件は既存データを即時破壊するものではないが、受理されたデータに対して新規実施回を開始できず、さらに意味上同一の案件 ID が併存しうるため、リリース前に解消すべき Major と判定する。

### 14.1 最大の指摘: 書き込みと取り込みの非対称（F12-33〜F12-37）

10角のうち4角が独立に同じ結論へ至った。**版数 1.3・1.4 で取り込み側へ足した上限に、書き込み側の対応物が無い。** その結果、画面から普通に作れるデータのエクスポートが再取り込みで拒否される。これは F12-01（取り込みだけが正規化規則を知らない）と F12-07（取り込み検査だけを足して往復保証を削った）と同型の退行であり、**リリース判定 A-11「ツール自身が生成した同一スキーマのJSONは、必ず再インポートできる」を破る**。

### 15.1 F12-36の独立再現

仕様書8.9.12は、作業項目実績1件だけでなく、実施回1件の合計秒が上限を超える入力についても「保存も取り込みも受け付けない」と定める。また9.3は、本ツールが書き出したJSONを同一バージョンへ必ず取り込めることを要求する。

実装を縦に追うと、取り込み側の `integrity.js.checkEffortRange()` は作業項目ごとの合計に加えて実施回合計も検査する。一方、通常writerの `intervalOps.checkEffortRange()` と `directEntryOps.accepted()` は変更対象の作業項目だけを検査する。アクション層は、変更後の `nextRun` を組み立てたあとに実施回合計を再検査せず `saveEntity()` / `saveEntities()` へ渡す。

動的プローブでは、同一実施回に2つの作業項目を用意し、各作業項目へ上限の60%に当たる `600,000,000,000` 秒の工数を設定した。

| 観測 | 結果 |
| ---- | ---- |
| 各作業項目のwriter判定 | `[true, true]`。各項目は上限内として受理 |
| 作業項目ごとの合計 | `[600000000000, 600000000000]` 秒 |
| 実施回合計 | `1200000000000` 秒。上限 `1000000000000` 秒を超過 |
| 同じデータのJSON取り込み | 拒否。「実施回の合計工数が上限を超える」 |

この反例により、F12-29の修正は作業項目単位では有効だが、実施回単位の通常保存契約は未完成であることを確認した。通常操作で保存できるデータを自己エクスポート後に復元できないため、F12-36は **Major** であり、リリース阻害事項である。

修正時は、`nextRun` の組み立て後かつ永続化前の共通境界で実施回合計を検査する。区間入力と直接入力の両方について「各作業項目は上限内・実施回合計だけが上限超過」のアクション層反例、拒否時に保存されないこと、export → import の往復を自動試験へ固定する必要がある。
