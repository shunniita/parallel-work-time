## 1. 指摘

### S8-1 集計済み後に未終了区間を作ると、転記値が未確定のまま転記済みにできる

- 重要度: **Major**（外部の正式な記録先へ渡せない状態を「転記済み」として保存できる）
- 対象: `src/domain/runStatus.js:49-63`、`src/app/actions/transferActions.js:70-100,218-229`、`tests/integration/transferActions.test.js:160-164,192-214`

実施回が集計済みでも `isRunEditable()` は `true` を返すため、区間操作を続けられる。集計済みになった後で新しい作業区間を開始すると、その実施回には再び未終了区間が存在する。

しかし、`changeStatus()` が `canAggregate()` を確認するのは「作業中 → 集計済み」だけである。「集計済み → 転記済み」では記録内容を再確認しない。画面のボタン制御に使う `previewStatusChange()` も同じ条件なので、ボタンは有効なままであり、アクション層も遷移を受け付ける。

最小ケースで次の状態を再現した。

```text
preview = { ok: true, reason: null }
status = transferred
openCount = 1
transferMinutesSum = null
```

これは、仕様書7章の「集計済みは未終了区間がなく、転記値を確認できる状態」という意味と、8.6.5の未確定値を壊す。転記値が存在しないのに転記完了日時が保存され、その後は閲覧のみとなるため、利用者は取り消し理由を記録して集計済みへ戻さないと区間を終了できない。

最低限、次をそろえて実装する。

1. 「集計済み → 転記済み」でも `canAggregate(current)` を確認し、未終了区間があればアクション層で拒否する。
2. `previewStatusChange()` も同じ条件で拒否し、ボタンを無効化して理由を示す。
3. 「集計済み → 作業開始 → 転記済み操作」を結合テストとE2Eへ追加し、画面制御と保存契約の両方を固定する。

別案として、集計済み状態で未終了区間を作る操作を拒否し、明示的に作業中へ戻してから再開させる方法もある。ただし、どちらを採用しても、保存済みデータへ `status="transferred"` と未終了区間が同居しないことをアクション層で保証する必要がある。

- 推奨対応時期: Step 8 の完了を宣言する前
- 状況: **対応済み（2026-08-06）。指摘のとおり再現した。** 対応前の実測値は `preview={ok:true}`、`status=transferred`、`openCount=1`、`transferMinutesSum=null`、`transferredAt` 設定済みの同居である。

  提示された対応1と2を採った（別案の「集計済みでの未終了区間の作成を拒否する」は採らない。仕様書7.2 が閲覧のみとするのは転記済みとアーカイブだけであり、集計済みでの編集を止めるのは仕様の変更にあたる）。

  `requiresClosedIntervals(from, to)` を新設し、`changeStatus()` と `previewStatusChange()` の両方が同じ条件を使う。条件は「転記済みへ入るとき」または「作業中から集計済みへ入るとき」である。転記済みから戻すときは確かめない（まさにその未終了区間を直すための操作であり、中身を理由に拒むと直す手段が無くなる）。

  判定を1つの関数へ寄せたのは、画面とアクション層で条件がずれると「押せるボタンをアクション層が拒む」形になり、押してから初めて理由を知ることになるためである。

  対応3として結合テスト6件（拒否、拒否後の状態と `transferredAt`、理由の文言、画面制御、区間を閉じれば進める、直接入力だけなら進める）とE2E1件（集計済み→区間開始→ボタン無効→終了→進める）を追加した。

- 重要度: **Minor**（コピーした行の順序が仕様書8.7.7と異なり、転記時の照合を誤りやすくする）
- 対象: `docs/同時並行作業時間計測支援ツール_仕様書.md:484-490`、`src/domain/aggregate.js:130-152`、`src/ui/views/summaryView.js:140-151,469-480`、`tests/unit/ui/summaryView.test.js:249-299`

仕様書8.7.7は、クリップボードへコピーするテキストを外部項目コード順に並べると定めている。画面一覧は外部項目コード順と表示順を切り替えられるが、この表示上の選択がコピー契約を変えてはならない。

現在の `summaryView` は、選択中の並び順で作った `aggregate` をそのまま `buildTransferText()` へ渡す。`buildTransferText()` は受け取った `rows` の順序を信頼して反復するため、表示順を選択した後はコピー結果も表示順になる。

表示順と外部項目コード順が食い違うケースで、次を再現した。

```text
画面の表示順: X-2000, X-1100
実際のコピー: X-2000, X-1100
仕様上の順序: X-1100, X-2000
```

`buildTransferText()` が内部で行の複製を外部項目コードの自然順へ並べるか、コピー時に外部項目コード順の集計を別途作る。コピー形式の契約を呼び出し側の画面状態へ依存させない前者の方が、別画面や将来の呼び出し元でも破りにくい。

単体テストとE2Eには、既定の外部項目コード順でコピーするケースはあるが、「表示順へ切り替えた後にコピーしても外部項目コード順」というケースがない。修正と同時に追加する。

- 推奨対応時期: Step 8 の完了を宣言する前
- 状況: **対応済み（2026-08-06）。指摘のとおり再現した。** 対応前は表示順を選ぶとコピーが `X-2000, X-1100` になり、外部項目コード順（`X-1100, X-2000`）と食い違っていた。

  推奨された前者（`buildTransferText()` の中で並べ直す）を採った。呼び出し側の画面状態にコピー形式の契約を依存させないためである。行の配列は複製してから並べ替える。呼び出し側が表示に使っている配列をその場で並べ替えると、コピーしただけで画面の並びが変わる。

  単体テスト3件（表示順で集計してもコピーは外部項目コード順、両者の結果が一致、渡した集計結果を書き換えない）とE2E1件（表示順へ切り替えてコピーし、クリップボードの並びが `X-100, X-1000, X-1100, X-2000` であること）を追加した。

## 2. 成立を確認した契約

- 時刻入力分、直接入力分、合計秒、転記値を作業項目別に一覧表示する。
- 直接入力秒へ参加人数を掛けず、作業項目合計に対して一度だけ分単位へ切り上げる。
- 未終了区間を含む作業項目の転記値を未確定とし、確定済みの秒数と実施回小計を区別して表示する。
- 作業中から集計済みへ進む際、未終了区間があれば画面とアクション層の双方で拒否する。
- 外部項目コードを自然順で表示でき、未設定項目を末尾へ置いて警告する。
- 外部項目コード未設定または未確定の行をコピー対象から除き、除外件数と理由を通知する。
- `navigator.clipboard` が使えない場合に `execCommand('copy')` へフォールバックし、双方が失敗した場合は手動コピーを案内する。
- 作業項目単位の転記チェックを永続化せず、実施回単位の状態だけを保存する。
- 作業中・集計済み・転記済み間の許可された遷移だけを受け付け、自動遷移しない。
- 転記済みから集計済みへ戻す際は理由を必須とし、状態変更と変更履歴を同一トランザクションで保存する。
- 転記済みでは区間・直接入力・数量の変更を拒否し、取り消し後は再び編集できる。

## 5. mino系スキルの適用判断

- `mino-reproducible-development`: 仕様・設計・実装・単体／結合／E2E・最小再現をつなげて、Step 8 の完了条件を検証するため使用した。
- `mino-domain-model-completeness`: 作業中・集計済み・転記済みの意味、未終了区間、転記値の確定性という状態不変条件を確認し、S8-1の欠落を特定するため使用した。
- `mino-design-by-contract`: 状態遷移の事前条件、拒否時の不変性、コピー形式と並び順の事後条件を確認するため使用した。
- `mino-interface-implementation-separation`: 画面上の表示順と、外部へ渡すコピー形式の契約を分離して評価し、S8-2を特定するため使用した。
- `mino-architecture-quality-strategy`: 状態の正本に関係するため適用を迷ったが、複数システムの移行・回復設計やsystem-wideな目標構成ではなく、単一アプリ内の状態遷移契約として解決できるため使用しなかった。
