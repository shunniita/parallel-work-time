## 1. 要件の要約

### 1.1 ツールの目的

複数案件・複数作業項目・複数参加者が同時並行で進む状況において、作業時間と参加人数から**作業項目別の総工数**を記録・集計し、利用者が外部の正式な記録先へ**手作業で転記する**までを支援する。勤怠・給与・原価・実績保管の代替ではない。

### 1.2 中核となる計算モデル

これが本ツールの本質であり、実装上もここを最初に固める。

```text
作業区間秒 = floor((endAt - startAt) / 1000) × 参加者数
休憩区間秒 = 0
直接入力秒 = seconds（参加者数を掛けない）
作業項目合計秒 = Σ作業区間秒 + Σ直接入力秒
転記値分     = ceil(作業項目合計秒 / 60)
```

丸めの位置が要件である。**区間ごとには丸めず、作業項目合計に対して一度だけ分へ切り上げる**（8.6.4）。ミリ秒差は秒へ切り捨ててから人数を掛ける（8.6.1）。直接入力値はすでに人数を含んだ総工数であり、参加者数を掛けない（8.5.6、8.6.6）。

### 1.3 実行形態の制約

| 制約           | 内容                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------- |
| 静的Webアプリ  | HTML/CSS/JavaScript のみ。サーバー側プログラム・サーバー側DBなし（5.1.1、5.1.2）。             |
| 配信           | HTTP/HTTPS 経由。`file://` は動作保証外（5.1.3）。                                             |
| 外部依存禁止   | CDN・外部フォント・外部API・外部通信を一切使わない（5.1.4、13章）。                            |
| ビルド工程なし | 配布ZIPを展開してそのまま静的配信できる構成（5.1.5、推奨）。                                   |
| 保存先         | IndexedDB。`StorageAdapter` 経由に限定し、画面・計算層からIndexedDB APIを直接呼ばない（5.3）。 |
| 単一利用者     | 一管理者・一端末・一ブラウザプロファイル。同時編集・同期・認証は対象外（3.1、3.2）。           |

### 1.4 データ階層

```text
TaskTemplate（対象種別 × バリエーション × 版）
        │ 実施回作成時に「値として複製」
        ▼
ProjectGroup（案件ID・対象種別・バリエーション・総予定数）
   └─ WorkRun（実施回：作業日・今回数量・状態）
        └─ TaskRecord（作業項目実績）
             ├─ TimeInterval[]（work / break）
             └─ DirectEntry[]（直接入力）
```

テンプレート改訂は既存実施回へ自動反映しない（8.1.4、A-09）。これは実施回作成時に作業項目定義を値としてコピーすることで成立させる（6.3）。

## 2. 初版の画面構成

### 2.1 全体レイアウト

【仕様】画面幅1280px以上のPCを主対象とし、左に階層一覧、右に選択中の詳細を表示する二分割構成（12.1）。

├──────────────────────────────────────────────────────────────────────────────┤
│ ⚠ 警告領域（固定・常時）                                                       │
│   未終了区間 3件（うちしきい値超過 1件）  [未終了のみ絞り込み]                    │
│   ⚠ 同じデータを別のタブでも開いています。…                                     │
│   ⚠ 最終エクスポートから14日経過しています。 [エクスポート]                       │
├──────────────────────┬───────────────────────────────────────────────────────┤

│                      │                                                       │

警告領域・保存状態表示の具体的な配置は、仕様が「案件一覧上部の固定警告領域」（12.2）と「画面上へ表示」（9.1）のみを定めるため実装判断とする。

### 2.2 画面一覧と実装内容

仕様12.2 の7画面に対応させる。専用ルーティングは持たず、単一ページ内のビュー切替で実現する。

#### (1) 案件・実施回一覧（左ペイン常設）

- 案件ID → 実施回 → 作業項目の3階層ツリー（12.1）。
- 作業項目ノードに現在状態アイコン（未着手／作業中／休憩中／完了、7.2）。
- 実施回ノードに状態バッジ（作業中／集計済み／転記済み／アーカイブ／削除候補）。削除候補は派生判定（7章）。
- 絞り込み: 「未終了区間のあるものだけ」「作業中のみ」。専用画面を作らず絞り込みで代替する（12.2 末尾）。
- アーカイブ済み実施回は既定で非表示（アーカイブ画面で扱う）。

#### (2) 案件・実施回登録

案件登録フォーム（8.2.1）:

| 項目           | 入力             | 検証                                                                               |
| -------------- | ---------------- | ---------------------------------------------------------------------------------- |
| 案件ID         | テキスト（必須） | 8.9.1。**一意**。既存案件IDと対象種別が異なる場合は内容を示して登録を禁止（8.2.6） |
| 対象種別       | 選択（必須）     | テンプレート定義から候補                                                           |
| バリエーション | 選択（必須）     | 対象種別に紐づく候補                                                               |
| 総予定数       | 数値（必須）     | 1以上の整数（8.9.2）                                                               |

実施回登録フォーム（8.2.4、8.3.1、8.3.2）:

| 項目               | 入力                                | 検証                                                               |
| ------------------ | ----------------------------------- | ------------------------------------------------------------------ |
| 作業日             | 日付（既定=今日）                   | 同日複数可（8.2.3）                                                |
| 今回数量           | 数値（必須）                        | 1以上の整数。累計が総予定数を超える場合は警告し確認後続行（8.9.7） |
| 生成対象の作業項目 | チェックボックス一覧（既定=全選択） | 有効項目のみ表示（8.1.5、8.3.1）。除外可（8.3.2）                  |

作成時に `templateId` / `templateVersion` を記録し、作業項目定義を値として複製する（6.3、6.5）。

#### (3) 作業項目詳細

【仕様】時刻履歴、直接入力、参加者、工数内訳を表示・編集する（12.2）。

```text
作業項目A ｜ 外部コード: X-100 ｜ 状態: 作業中
──────────────────────────────────────────────────────────────────
[開始] [休憩] [再開] [終了] [参加者変更] [直接入力] [履歴編集] [区間追加]
                                          ← 状態に応じ活性/非活性（12.4）
──────────────────────────────────────────────────────────────────
区間履歴
 # 種別 開始日時              終了日時              人数 参加者        工数
 1 作業 2026-07-30T09:00:00+09:00 2026-07-30T09:20:00+09:00  3 甲,乙,丙   3600秒
 2 休憩 2026-07-30T09:20:00+09:00 2026-07-30T09:30:00+09:00  3 甲,乙,丙      0秒
 3 作業 2026-07-30T09:30:00+09:00 （未終了）                  2 甲,乙      ―
                                                       [編集][削除]
──────────────────────────────────────────────────────────────────
直接入力
 # 追加工数  参加者 備考                       登録日時
 1 20分00秒  甲     計測漏れ分を後から追加      2026-07-30T10:00:00+09:00
                                                       [編集][削除]
──────────────────────────────────────────────────────────────────
工数内訳   時刻入力 3600秒 ／ 直接入力 1200秒 ／ 確定分合計 4800秒
           転記値 未確定（進行中1件）
```

- 未終了区間があるため転記値は未確定。確定分の小計は表示する（8.6.5）。
- 直接入力の見出しは「追加工数」または「総工数（人×時間）」とする（8.5 補足）。
- 終了日時の手入力補完が可能（8.8.4）。自動推定は行わない（8.8.5）。
- 参加者入力は自由文字列＋過去入力候補（8.4.6、8.4.7、8.9.9）。

参加者変更ダイアログ（8.4.10、補足2）:

```text
参加者変更
  変更時刻  [2026-07-30T09:30:00+09:00]   ← 初期値=現在日時
  変更後の参加者  [甲][乙] + [追加…]
  ────────────────────────────────
  09:00～09:30 の区間を確定し、09:30 から新しい区間を開始します。
  [キャンセル] [変更する]
```

#### (4) 集計・転記

実施回単位の作業項目別一覧（8.7.1〜8.7.3）。

```text
実施回: PJ-0001 / 第1回 2026-07-30 / 数量50 ｜ 状態: 集計済み
並び順: [外部項目コード順（自然順）▼ / 表示順]
 外部コード 作業項目   時刻入力分 直接入力分 合計秒 転記値  ✓
 X-100     作業項目A      60分      20分   4800    80分  [ ]
 X-200     作業項目B      30分       0分   1800    30分  [ ]
 (未設定)⚠ 作業項目C      10分       0分    600    10分  [ ]
──────────────────────────────────────────────────────
合計 … [転記値をコピー] [実施回を転記済みにする]
```

- 外部項目コード順は自然順、未設定は末尾へ置き警告表示（8.7.3、8.7.4）。
- コピー形式は `外部項目コード<TAB>転記値分` の行（8.7.7）。
- 右端の `✓` は**保存しない画面上の一時チェック**（8.7.5）。リロードで消えることを明示する。
- 転記済み管理は実施回単位のみ（8.7.6）。
- 未終了区間があるうちは実施回を集計済み以降へ進められない（8.9.6、A-08）。

#### (5) 作業テンプレート

- 対象種別×バリエーションごとのテンプレート一覧（有効版のみ表示）。
- 作業項目の名称・外部項目コード・表示順・有効状態の編集（8.1.2）。
- 「改訂して保存」で `version` を繰り上げ、新しい `templateId` を発行する。`templateSeriesId` は不変（6.3）。
- 旧版レコードは保持するが、旧版の閲覧・比較画面は設けない（6.3、12.2）。
- サンプルJSONからの初期投入（8.1.6）。

#### (6) アーカイブ

- 転記済み／アーカイブ／削除候補の一覧（10.1、10.3）。
- 「アーカイブへ移動」は利用者操作（10.1）。実行時に `archivedAt` を記録する。
- 削除候補は `archivedAt` + `retentionDays` 経過分（10.3）。
- 完全削除は確認ダイアログ経由のみ（10.4、10.6）。実行前に共通の退避エクスポートを促す（9.4、10.5）。

#### (7) 設定・バックアップ

- 保持期間 `retentionDays`（初期30、10.2）。
- 未終了しきい値 `longRunningThresholdHours`（初期12、8.8.3）。
- JSONエクスポート（9.2）／インポート（9.3、全置換・確認・`schemaVersion` 一致検証）。
- 定期エクスポートの案内文（9.5）。
- スナップショット復元UIは設けない（9.4）。

### 2.3 作業項目の操作ボタン活性条件

| 作業項目の状態               | 開始                          | 休憩 | 再開 | 終了 | 参加者変更 | 直接入力 | 履歴編集 | 区間追加 |
| ---------------------------- | ----------------------------- | ---- | ---- | ---- | ---------- | -------- | -------- | -------- |
| 未着手                       | 活性                          | 非   | 非   | 非   | 非         | 活性     | 非       | 活性     |
| 作業中                       | 非                            | 活性 | 非   | 活性 | 活性       | 活性     | 活性     | 活性     |
| 休憩中                       | 非                            | 非   | 活性 | 活性 | 活性       | 活性     | 活性     | 活性     |
| 完了                         | 活性                          | 非   | 非   | 非   | 非         | 活性     | 活性     | 活性     |
| 実施回が転記済み／アーカイブ | すべて非活性（閲覧のみ、7.2） |

`完了` は不可逆ではなく、未終了区間が存在しないことを表す派生値である。再び開始すれば `作業中` へ戻る（7.2）。

ボタンの処理は 12.4 の表に従う。要点は次のとおり。

- 休憩: 進行中の work 区間を指定時刻で終了し、同時刻から break 区間を開始。参加者は直前の work 区間から引き継ぐ（8.9 補足）。
- 再開: 進行中の break 区間を指定時刻で終了し、同時刻から work 区間を開始。
- 参加者変更: 進行中区間を指定時刻で終了し、新しい参加者一覧で**同じ種別**の区間を同時刻から開始（8.4.10、補足2）。休憩中に一部だけ戻る場合も表現できる。
- 区間追加: 開始・終了日時を指定して手動追加。既存区間と重複しても保存を禁止せず警告のみ（8.4.11、8.9.5）。

ボタン操作による未終了区間は作業項目ごとに一つまで（8.4 補足1、A-17）。

## 3. データ構造

### 3.1 保存レイアウト（IndexedDB オブジェクトストア）

| ストア          | キー                   | 内容                                 | 索引                                       |
| --------------- | ---------------------- | ------------------------------------ | ------------------------------------------ |
| `settings`      | 固定キー `"singleton"` | Settings（6.2）                      | —                                          |
| `taskTemplates` | `templateId`           | TaskTemplate（6.3）。旧版も保持      | `templateSeriesId`、`targetType`+`variant` |
| `projectGroups` | `projectGroupId`       | ProjectGroup（6.4）                  | `projectId`（一意）                        |
| `workRuns`      | `runId`                | WorkRun＋tasks配下すべて（6.5〜6.8） | `projectGroupId`、`status`、`workDate`     |
| `changeHistory` | `historyId`            | 簡易変更履歴（11章）                 | `targetId`、`timestamp`                    |

`taskTemplates` の複合索引に `active` を含めない理由: IndexedDB の有効なキー型は number / string / Date / ArrayBuffer / Array に限られ、boolean は含まれない。複合索引のキーパスのいずれかが無効なキーを返すと、そのレコードは例外なく索引から除外される。有効版の絞り込みは `targetType`+`variant` で取得した結果に対しメモリ上で行う。他の索引に boolean を用いるものはない（`status` / `workDate` / `projectId` / `targetId` / `timestamp` はいずれも文字列）。

WorkRun は `tasks[] → intervals[] / directEntries[]` を内包する単一ドキュメントとして扱う（6.5〜6.8 の入れ子表記に従う）。区間1件の編集でも WorkRun 1件を書き戻す粒度になるが、初版の性能目標（案件20件・実施回100件・区間2,000件、13章）に対しては十分である。区間の一覧・集計は選択中の実施回のみメモリへ展開する。

スナップショット用のストアは設けない（9.4）。

### 3.1.1 `StorageAdapter` へ追加した操作

仕様書5.3 は「最低限、次の操作を定義する」として6操作を挙げる。画面・計算層から IndexedDB API を直接呼ばせないため、次を追加した。

| 操作                                                   | 追加理由                                                                                                                                                                                                   |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `saveEntities(entries)`                                | 一連の関連書き込みを同一トランザクションへまとめる（9.1）。テンプレート改訂は「新版の追加」と「旧版の無効化」が同時に成立しなければ整合せず、`saveEntity` の連続呼び出しでは有効版が2つ並ぶか0個になりうる |
| `findTaskTemplates(targetType, variant, {activeOnly})` | 索引を画面から使うため。`activeOnly` は取得後にメモリ上で絞り込む（前項の理由）                                                                                                                            |
| `findTemplateSeries(templateSeriesId)`                 | 版系列を辿る（6.3）                                                                                                                                                                                        |
| `findProjectGroupByProjectId(projectId)`               | 案件IDの一意性検証（8.2.6）                                                                                                                                                                                |
| `exportAll({exportedAt})`                              | `exportedAt` を任意で受け取る。渡さなければ現在時刻を使う。エクスポート往復のテストを決定的にするため                                                                                                      |

いずれも `IndexedDbAdapter` と `MemoryAdapter` の両方へ同一の契約テストを通す。

### 3.4 派生値（保存しない計算結果）

| 派生値                  | 定義                                                                                         |
| ----------------------- | -------------------------------------------------------------------------------------------- |
| 区間工数秒              | `type === "break" ? 0 : floor((endAt - startAt)/1000) * participants.length`（8.6.1、8.6.2） |
| 作業項目 時刻入力秒     | 当該項目の全区間工数秒の合計。未終了区間は含めない                                           |
| 作業項目 直接入力秒     | `Σ directEntries[].seconds`（8.6.3、8.6.6）                                                  |
| 作業項目 合計秒         | 上2つの和                                                                                    |
| 作業項目 転記値分       | `ceil(合計秒 / 60)`。未終了区間があれば未確定。確定分小計は表示（8.6.5）                     |
| 作業項目 現在状態       | 未着手／作業中／休憩中／完了（7.2）                                                          |
| 実施回 集計済み遷移可否 | 未終了区間が無いこと（8.9.6）                                                                |
| 案件 累計数量・残数     | `Σ runQuantity`（アーカイブ含む）／`totalQuantity - 累計`（8.2.5）。残数は負値を許す。累計超過は警告のうえ続行できるため（8.9.7）、0で止めると超過量が分からなくなる |
| 削除候補                | `status === "archived"` かつ `archivedAt + retentionDays < 現在日時`（10.3）                 |
| しきい値超過            | `現在日時 - startAt > longRunningThresholdHours`。1分ごとに再評価（8.8）                     |
| 参加者候補              | 全 `participants[]` からの一意集合（8.4.7）                                                  |

### 5.1 順序の根拠

- Step 2 を最優先にする理由: 工数計算と丸め位置（8.6.4）が本ツールの価値そのものであり、受入試験のうち複数が計算に集約する。UIより先に純関数として確定させ、テストで固定する。
- Step 3 を UI より前に置く理由: 5.3 が保存処理の分離を明示要件としているため、後付けにすると層の分離が崩れる。
- Step 4→5 の順: 実施回作成がテンプレートに依存する（8.3.1）。
- Step 6 に参加者変更を含める理由: 参加者の途中増減は本ツールの中心的な用途であり（2章）、後回しにしない。実装は既存の終了・開始処理の組み合わせで済む。
- 転記済みからの後退（11章）を Step 8 で実装する理由: Step 8 が転記済み管理（8.7.6）を含むため、この段階で「転記済みへ進めるが戻せない」状態が生じる。戻す操作は 11章が理由の記録を求める操作であり、区間・直接入力の削除と同じ理由で、操作と履歴を同時に入れる。Step 10 に残るのは他の2操作（実施回の削除、案件グループの削除）である。
- 区間削除の変更履歴（11章）を Step 6 で実装する理由: Step 6 が区間削除を含む一方、簡易変更履歴は Step 10 である。そのままでは Step 6〜9 の間「履歴を残さずに区間を削除できる」期間が生まれ、11章を満たさない記録が実データへ残る。`changeHistory` のスキーマと検証は Step 3 で用意済みのため、削除と同時に1件書き込む（設計メモ PWT-DESIGN-006 §6.1 の案B）。Step 7 の直接入力の削除も同じ理由で同時に実装した。Step 10 に残るのは他の3操作（転記済みからの後退、実施回の削除、案件グループの削除）である。
- Step 9 を Step 10 より前に置く理由: 9.4 の退避処理を削除操作から呼ぶため、先にエクスポート経路が必要。
- 保存成否表示（9.1）と Quota 対応を Step 3 で実装した理由: 保存の失敗が沈黙する期間を作らないため、`StorageAdapter` の導入と同時に成否の分類（`QuotaExceededError` の捕捉とエクスポート・削除の案内を含む）と表示経路を通した。未終了区間への終了時刻補完（8.8.4）も、区間編集の一部として Step 6 で実装済みである。したがって Step 11 の内容欄にこれらは含めない。

### 5.2 各段階に共通する完了条件

- `domain/` の変更には単体テストを添える。
- 保存を伴う操作は `StorageAdapter` 経由であることを確認する。
- リロード後にデータが復元することを確認する（9.1）。
- 外部通信を発生させていないことを確認する（Network タブが空、13章、A-15）。

## 8. テスト方針

### 8.1 方針の骨子

1. **計算は純関数の単体テストで固定する。** 工数計算・丸め・状態判定・検証は `domain/` に閉じ込め、UIを経由せずに網羅する。計算系の受入試験（T-04〜T-07、T-13、T-16）は単体テストで先に固定し、E2Eでも再確認する。
2. **保存はアダプター差し替えでテストする。** `StorageAdapter`（5.3）が定義済みのため、`MemoryAdapter` と `fake-indexeddb` で結合テストを行う。
3. **受入試験 T-01〜T-18 はE2Eで自動化する。** 仕様16章の試験表をそのままテストIDにし、追跡可能にする。
4. **外部通信ゼロ（13章、A-15）はテストで機械的に検証する。** E2Eでネットワーク要求を全遮断し、要求が発生したら失敗させる（T-18）。
5. **架空データのみを使う（14章）。** フィクスチャは `対象種別A`／`参加者甲` 等の抽象名に限定する。

### 8.3 実行環境と依存

§4.3 のとおり、開発時のみ Node ツールを使う構成で確定した。`mise.toml` に node 24 が既にあるため追加設定は不要。

```text
npm test          → 単体＋結合テスト
npm run test:e2e  → E2E（Chromium、静的配信を自動起動）
```

- 依存はすべて devDependencies。実行時の依存は増やさない（5.1.4）。
- ブラウザバイナリは配布物へ含めない。
- ライセンスは MIT / BSD / Apache-2.0 に限る（14章）。

採用しなかった代替案: `tests/runner.html` に自作テストランナーを置き、`domain/` の単体テストのみ自動化する。結合・E2Eは16章の試験表を手動チェックリストとして運用する。T-11／T-12／T-14／T-18 のような回帰しやすい項目が手動になり、品質維持のコストが上がるため採らない。
