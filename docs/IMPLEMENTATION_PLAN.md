## 1. 要件の要約

### 1.1 ツールの目的

複数案件・複数作業項目・複数参加者が同時並行で進む状況において、作業時間と参加人数から**作業項目別の総工数**を記録・集計し、利用者が外部の正式な記録先へ**手作業で転記する**までを支援する。勤怠・給与・原価・実績保管の代替ではない。

### 1.2 中核となる計算モデル

これが本ツールの本質であり、実装上もここを最初に固める。

```text
作業区間秒 = floor((endAt - startAt) / 1000) × 参加者数
休憩区間秒 = 0
作業項目合計秒 = Σ作業区間秒 + Σ直接入力秒
転記値分     = ceil(作業項目合計秒 / 60)
```

丸めの位置が要件である。**区間ごとには丸めず、作業項目合計に対して一度だけ分へ切り上げる**（8.6.4）。ミリ秒差は秒へ切り捨ててから人数を掛ける（8.6.1）。

### 1.3 実行形態の制約

| 制約 | 内容 |
| ---- | ---- |
| 静的Webアプリ | HTML/CSS/JavaScript のみ。サーバー側プログラム・サーバー側DBなし（5.1.1、5.1.2）。 |
| 配信 | HTTP/HTTPS 経由。`file://` は動作保証外（5.1.3）。 |
| 外部依存禁止 | CDN・外部フォント・外部API・外部通信を一切使わない（5.1.4、13章）。 |
| ビルド工程なし | 配布ZIPを展開してそのまま静的配信できる構成（5.1.5、推奨）。 |
| 保存先 | IndexedDB。`StorageAdapter` 経由に限定し、画面・計算層からIndexedDB APIを直接呼ばない（5.3）。 |
| 単一利用者 | 一管理者・一端末・一ブラウザプロファイル。同時編集・同期・認証は対象外（3.1、3.2）。 |

### 1.4 データ階層

```text
TaskTemplate（対象種別 × バリエーション × 版）
        │ 実施回作成時に「値として複製」
        ▼
ProjectGroup（案件ID・対象種別・バリエーション・総予定数）
   └─ WorkRun（実施回：作業日・今回数量・状態）
        └─ TaskRecord（作業項目実績）
             ├─ TimeInterval[]（work / break）
             └─ DirectEntry[]（直接入力）
```

テンプレート改訂は既存実施回へ自動反映しない（8.1.4、A-09）。これは実施回作成時に作業項目定義を値としてコピーすることで成立させる（6.3）。

### 1.5 必須機能の要約

| 領域 | 必須の要点 |
| ---- | ---------- |
| テンプレート管理 | 対象種別×バリエーション単位の作業項目登録、外部項目コード・表示順・有効状態、版番号繰り上げと旧版保持、無効項目は新規実施回へ生成しない（8.1.1〜8.1.5）。 |
| 案件管理 | 案件登録、同一案件IDに複数実施回、同日複数実施回、総予定数/累計/残数表示、案件IDと対象種別の不一致警告、数量の後修正（8.2.1〜8.2.7）。 |
| 作業項目生成 | 選択に応じた有効項目の表示、実施回作成前の除外操作（8.3.1、8.3.2）。 |
| 時刻入力 | 作業開始/休憩/再開/終了、任意回数の繰り返し、初期値=現在日時、オフセット付きISO 8601（秒精度）、後編集、複数参加者、日跨ぎ、**複数作業項目の同時作業中**（8.4.1〜8.4.9）。 |
| 直接入力 | 分・秒で加算、備考必須、負値禁止（8.5.1〜8.5.5）。 |
| 工数計算 | §1.2 のとおり。未終了区間を含む項目の転記値は未確定表示（8.6.5）。 |
| 集計・転記 | 実施回単位の項目別一覧、時刻入力分/直接入力分/合計秒/転記値、外部項目コード順、作業項目単位と実施回単位の転記済み管理（8.7.1〜8.7.6）。 |
| 未終了・異常 | 未終了区間の警告領域表示、しきい値超過の強調（初期12時間、設定変更可）、終了時刻の手入力補完、**自動推定を行わない**（8.8.1〜8.8.5）。 |
| 入力検証 | 必須項目、数量は1以上の整数、終了≧開始（同一日時は0秒で許可）、参加者0人の保存禁止、区間重複警告、未終了があれば集計済みにできない、累計超過は警告して続行可、表記ゆれは警告しない（8.9.1〜8.9.9）。 |
| 複数タブ | `BroadcastChannel` 等で検知し警告表示。ロックは不要（8.10、A-13）。 |
| 保存・バックアップ | 操作後の即時保存と成否表示、`QuotaExceededError` 捕捉、JSON全量エクスポート、インポートは全置換＋検証失敗時は無変更、破壊的操作直前のスナップショット3世代（9章）。 |
| 保持・削除 | アーカイブ移動、初期保持期間30日（設定可）、削除候補表示、完全削除は確認操作のみ、無確認自動削除なし（10章）。 |
| 変更履歴 | 全面監査ログなし。`createdAt`/`updatedAt` と、5種の操作に限る簡易変更履歴（11章）。 |
| 画面 | 1280px以上のPC主対象、左ツリー＋右詳細の二分割、7画面（12章）。 |

### 2.3 作業項目の操作ボタン活性条件

【仕様】12.4 は「現在状態に応じて有効な操作だけを活性化する」と定めるが、状態と各ボタンの対応表は仕様に存在しない。下表は【暫定解釈】である（§6.2-A で仕様化を提案）。

| 作業項目の現在状態 | 開始 | 休憩 | 再開 | 終了 | 直接入力 | 履歴編集 |
| ------------------ | ---- | ---- | ---- | ---- | -------- | -------- |
| 未着手（区間なし）  | 活性 | 非   | 非   | 非   | 活性     | 非       |
| 作業中（work未終了）| 非   | 活性 | 非   | 活性 | 活性     | 活性     |
| 休憩中（break未終了）| 非  | 非   | 活性 | 活性 | 活性     | 活性     |
| 完了（未終了なし、区間あり）| 活性 | 非 | 非 | 非 | 活性 | 活性 |
| 実施回が転記済み／アーカイブ | すべて非活性（7章「転記済みの実施回は…工数を編集できない」） |

ボタンの意味【暫定解釈】:

- 開始: `type="work"` の区間を `startAt=現在日時` で作成（`endAt=null`）。
- 休憩: 進行中の work 区間を現在日時で終了し、同時刻から `type="break"` 区間を開始。
- 再開: 進行中の break 区間を現在日時で終了し、同時刻から `type="work"` 区間を開始。
- 終了: 進行中の区間を現在日時で終了する（新規区間は作らない）。

いずれも各日時の初期値は現在日時（8.4.3）とし、確定前に編集可能とする。

## 3. データ構造

### 3.1 保存レイアウト（IndexedDB オブジェクトストア）

【仕様】5.2・5.3 は保存先と `StorageAdapter` の操作を定めるが、ストア分割は定めていない。下表は【暫定解釈】。

| ストア | キー | 内容 | 備考 |
| ------ | ---- | ---- | ---- |
| `settings` | 固定キー `"singleton"` | Settings（6.2） | 単一レコード |
| `taskTemplates` | `templateId` | TaskTemplate（6.3） | 旧版も保持 |
| `projectGroups` | `projectGroupId` | ProjectGroup（6.4） | `projectId` に索引 |
| `workRuns` | `runId` | WorkRun＋tasks配下すべて（6.5〜6.8） | `projectGroupId`・`status`・`workDate` に索引 |
| `changeHistory` | `historyId` | 簡易変更履歴（11章） | `targetId`・`timestamp` に索引 |
| `snapshots` | 連番または生成ID | 全体スナップショット（9.4） | 直近3世代のみ保持 |

WorkRun は `tasks[] → intervals[] / directEntries[]` を内包する単一ドキュメントとして扱う（6.5〜6.8 の入れ子表記に従う）。区間1件の編集でも WorkRun 1件を書き戻す粒度になるが、性能目標（案件100件・実施回1,000件・区間20,000件、13章）に対しては、1実施回あたりの区間数が現実的な範囲に収まる限り問題にならない。区間の一覧・集計は選択中の実施回のみメモリへ展開する。

### 3.4 派生値（保存しない計算結果）

保存せず、都度計算する。二重管理による不整合を避ける。

| 派生値 | 定義 |
| ------ | ---- |
| 区間工数秒 | `interval.type === "break" ? 0 : floor((endAt - startAt)/1000) * participants.length`（8.6.1、8.6.2） |
| 作業項目 時刻入力秒 | 当該項目の全区間工数秒の合計 |
| 作業項目 直接入力秒 | `Σ directEntries[].seconds`（8.6.3） |
| 作業項目 合計秒 | 上2つの和 |
| 作業項目 転記値分 | `ceil(合計秒 / 60)`（8.6.4）。未終了区間があれば「未確定」（8.6.5） |
| 作業項目 現在状態 | 未着手／作業中／休憩中／完了（§2.3） |
| 実施回 派生状態 | 未終了区間の有無から「集計済みへ遷移可能か」を判定（8.9.6） |
| 案件 累計数量・残数 | `Σ runQuantity`（アーカイブ含む）／`totalQuantity - 累計`（8.2.5） |
| 削除候補 | アーカイブ状態かつ保持期間経過（10.3、基準日は §6.2-C） |
| 参加者候補 | 全 `participants[]` からの一意集合（8.4.7） |

### 5.1 順序の根拠

- Step 2 を最優先にする理由: 工数計算と丸め位置（8.6.4）が本ツールの価値そのものであり、受入試験15件のうち5件が計算に集約する。UIより先に純関数として確定させ、テストで固定する。
- Step 3 を UI より前に置く理由: 5.3 が保存処理の分離を明示要件としているため、後付けにすると層の分離が崩れる。
- Step 4→5 の順: 実施回作成がテンプレートに依存する（8.3.1）。
- Step 9 を Step 10 より前に置く理由: 9.4 のスナップショットはインポートと削除の直前に作るため、先にインポート経路と検証が必要。エクスポートが動けば、以降の破壊的操作の検証も安全に行える。
- Step 11 を後段に置く理由: 横断的な警告・検証は対象画面が揃った後に一括で通した方が漏れが出にくい。ただし Step 5〜8 の各段階でも該当する必須検証（8.9.1〜8.9.4、8.9.6、8.9.7）はその場で実装する。

### 5.2 各段階に共通する完了条件

- `domain/` の変更には単体テストを添える。
- 保存を伴う操作は `StorageAdapter` 経由であることを確認する。
- リロード後にデータが復元することを確認する（9.1）。
- 外部通信を発生させていないことを確認する（Network タブが空、13章、A-15）。

## 6. 仕様上の矛盾や不足

仕様の変更は行わない。以下は確認が必要な事項の列挙と、実装を進めるための暫定解釈である。

### 6.1 優先度の高い5件（Step 1 で確認を要する）

| ID | 事項 | 影響 |
| -- | ---- | ---- |
| A | 作業項目の状態定義と操作ボタンの活性条件が未定義 | 12.4 の実装が確定しない |
| C | アーカイブ移行の自動/手動、および保持期間の起算日が未定義 | 10.2/10.3/A-10 の判定が確定しない |
| D | 直接入力の `seconds` に参加者数を掛けるかが両義的 | 工数が最大で人数倍ずれる |
| I | 参加者の途中増減の記録方法が未定義 | 背景（2章）の主要ユースケースが手順として成立しない |
| J | 同一作業項目に同時進行の区間を複数持てるかが未定義 | 8.4.9 と 12.4 の整合が取れない |

### 6.2 詳細

#### A. 作業項目の状態と操作ボタンの対応が未定義（不足）

- 7章の状態は**実施回**のものであり、作業項目の状態は定義されていない。一方 12.3 は行に「現在状態」を表示せよと定め、12.4 は「現在状態に応じて有効な操作だけを活性化」せよと定める。
- 【暫定解釈】§2.3 の状態4種（未着手／作業中／休憩中／完了）と活性条件表を用いる。
- 【変更提案】作業項目状態を仕様へ追記し、各ボタンの意味（特に「休憩」が work を終了して break を開始する複合操作である点）を明記する。

#### B. `templateId` が版をまたいで同一かが未定義（曖昧）

- 6.3 は `templateId` と `version` を持ち「改訂時は版番号を繰り上げ、旧版を保持する」とする。旧版を保持するなら、同一 `templateId` のレコードが複数存在するか、版ごとに別 `templateId` を持つかで、キー設計が変わる。6.5 の WorkRun は `templateId` と `templateVersion` を別に持つため、`templateId` は版共通の識別子と読むのが自然である。
- 【暫定解釈】ストア主キーは `templateId` とし、6.1 の内部固有IDの原則に従って**版ごとに別レコード＝別 `templateId`** とする。版系列は `targetType` + `variant` + `version` で辿り、WorkRun からは `templateId` で当該版を直接参照できる。
- 【変更提案】どちらの設計かを仕様で明記する。版系列を表す `templateSeriesId` を追加すれば曖昧さはなくなるが、初版では不要と考える。

#### C. アーカイブ移行の契機と保持期間の起算日（矛盾・不足）

- 7.1 は「転記済み → アーカイブ: 転記済みに変更した時点、または利用者操作」とし、自動と手動の両方を読める。一方 10.1 は「転記済みの実施回をアーカイブへ移動**できる**」と手動を示唆する。両者が並ぶと、転記済み状態が実質的に存在しない（即アーカイブ）のか、独立した状態として残るのかが決まらない。
- さらに 10.2/10.3 の保持期間の**起算日が指定されていない**。`transferredAt`（6.5）はあるが `archivedAt` はない。手動アーカイブを認める場合、起算日を `transferredAt` にするか実際のアーカイブ時点にするかで削除候補になる日が変わる。
- また `削除候補` は「保持期間を経過し、手動削除できる」状態（7章）であり、時間経過で自動的に成立する。`status` に保存すると、保存済み値と現在日時からの判定が食い違い得る。
- 【暫定解釈】(1) アーカイブは利用者操作で行い、転記済みは独立した状態として残す。(2) 保持期間の起算日は `transferredAt` とする。(3) `削除候補` は保存せず、`status === "archived"` かつ `transferredAt + retentionDays < 現在日時` の導出値とする。
- 【変更提案】7.1 の「転記済みに変更した時点、または利用者操作」を一方へ確定し、起算日を明記する。手動アーカイブ時点を起算日にするなら `WorkRun.archivedAt` の追加が必要。

#### D. 直接入力の `seconds` と参加者数の関係（曖昧）

- 4章は工数を「作業時間と参加人数を掛けた合計作業時間」と定義する。8.5.1 は「分および秒で**工数**を直接追加できる」と書き、6.8 の DirectEntry は `seconds` と `participants[]` の両方を持つ。この記述だけでは `seconds` に人数を掛けるとも読める。
- 一方 8.6 の式は `作業項目合計秒 = 作業区間秒の合計 + 直接入力秒の合計` であり、掛けない。T-06（作業40分＋直接入力20分＝転記値60分）もこの読みと一致する。
- 【暫定解釈】`seconds` は既に人数を含んだ工数そのものとし、**参加者数を掛けない**。`participants[]` は補助情報。
- 【変更提案】8.5.1 の文へ「入力値は人数を含んだ工数であり、参加者数を掛けない」ことを明記する。UI 上も「工数（人×分）」等のラベルで誤入力を防ぐ。

#### E. 簡易変更履歴の `targetType` が業務用語と衝突（命名）

- 11章の履歴フィールド `targetType` はエンティティ種別を指すが、4章の「対象種別」も `targetType`（6.3、6.4）である。同名で意味が異なり、混同しやすい。
- 【暫定解釈】履歴側の値は `"projectGroup"` 等のエンティティ名とし、実装内のコメントで区別する。
- 【変更提案】履歴側を `entityType` へ改名する。

#### F. 履歴の `reason` の必須性と入力方法が未定義（不足）

- 11章は `reason` を列挙するが、必須か任意か、どの操作で利用者へ入力させるかを定めていない。
- 【暫定解釈】任意入力。「転記済み状態からの後退」（7.1 で警告確認を伴う遷移）でのみ入力欄を表示し、他の操作では省略する。
- 【変更提案】必須とする操作を仕様で特定する。

#### G. 変更履歴・スナップショットがエクスポート対象外（不足）

- 9.2 のエクスポートJSONは `settings` / `taskTemplates` / `projectGroups` / `workRuns` の4種のみで、11章の簡易変更履歴を含まない。一方 T-11 は「エクスポートJSONをインポートし、**全データ**と集計値が一致する」ことを求める。厳密に読むと履歴が失われるため T-11 を満たさない。
- スナップショット（9.4）は復元用の内部データであり、エクスポートへ含めない設計は妥当と考える。
- 【暫定解釈】9.2 の列挙に従い履歴を含めない。T-11 の「全データ」は 9.2 の4種を指すものとして検証する。
- 【変更提案】(a) `changeHistory` をエクスポートへ追加する、または (b) T-11 の判定範囲を「9.2 に列挙したデータ」と明記する。どちらでも実装コストは小さい。(a) を推す。

#### H. エクスポート名と `.gitignore` の不一致（矛盾）

- 9.2 のファイル名は `parallel-work-time_YYYYMMDD-HHmmss.json`。5.4 の `.gitignore` 指定は `work-data_*.json` で、実際のエクスポートファイルに一致しない。14章・A-15 が求める「実データをリポジトリへ含めない」保証が抜ける。
- 【暫定解釈】§4.4 のとおり `parallel-work-time_*.json` を追加する。
- 【変更提案】5.4 の一覧を 9.2 のファイル名へ合わせる。

#### I. 参加者の途中増減の記録手順が未定義（不足・重要）

- 2章は「参加者が途中で増減する」を主要な背景として挙げる。しかし記録手段は「一つの作業区間へ複数の参加者名を登録できる」（8.4.6）だけであり、TimeInterval は参加者集合を1つしか持たない（6.7）。12.4 のボタンにも「参加者変更」に相当する操作がない。
- 現在の仕様で増減を表すには、進行中区間をその時刻で終了し、新しい参加者集合で別区間を開始する必要がある。この操作は仕様に記述されていない。
- 【暫定解釈】区間の参加者を後編集で修正するか、「終了→開始」を手動で2操作行う運用とする（8.4.5 の編集機能で表現可能）。
- 【変更提案】「参加者変更」操作（現時刻で区間を分割し、新しい参加者集合で継続する）を 8.4 と 12.4 へ追加する。初版で入れるべき価値が高い一方、実装は既存の終了・開始処理の組み合わせで済む。

#### J. 同一作業項目内に同時進行の区間を複数持てるか（曖昧）

- 8.4.9 は「複数の**作業項目**を同時に作業中の状態にできる」と定め、項目間の並行は明示する。同一項目内の並行（例: 甲乙が9:00〜、丙が9:30〜）は明示されていない。8.9.5 は「同一作業項目内で作業区間が重複する場合は**警告する**」とあり、禁止ではないため重複の存在を許容している。
- 一方 12.4 のボタン設計（開始／休憩／再開／終了）は、項目ごとに進行中区間が1つであることを前提とする。両者は同時には成り立たない。
- 【暫定解釈】ボタン操作では項目あたり進行中区間を1つに限る。区間の**手動追加・編集**では重複を許し、8.9.5 の警告のみ出す。
- 【変更提案】この方針を仕様へ明記する。あるいは 12.4 とは別に「区間を手動追加」操作を 8.4 へ明記する。

#### K. 休憩区間の参加者0人禁止が適用されるか（曖昧）

- 4章は「作業区間」を「作業**または休憩**の時間帯」と定義する。したがって 8.9.4「作業区間の参加者が0人の場合は保存を禁止する」は休憩区間にも及ぶと読める。しかし休憩の工数は常に0（8.6.2）であり、参加者を必須にする意味は薄い。
- 【暫定解釈】休憩区間にも参加者1名以上を要求し、「休憩」ボタン操作では直前の work 区間の参加者集合を引き継いで自動設定する（利用者の追加入力なしで検証を通す）。
- 【変更提案】8.9.4 を「`type="work"` の区間について」と限定するか、休憩の参加者引き継ぎを明記する。

#### L. 実施回単位と作業項目単位の転記済みの関係（不足）

- 8.7.5（作業項目単位）と 8.7.6（実施回単位）が併存するが、両者の従属関係が未定義。全項目が転記済みでないと実施回を転記済みにできないのか、独立なのか。実施回を転記済みへ変更したとき各項目も転記済みになるのか。転記済みから後退したとき項目側はどうなるのか。
- 【暫定解釈】(1) 実施回を転記済みにする際、未転記の項目が残っていれば確認を表示し、続行時は全項目を転記済みにする。(2) 実施回を集計済みへ戻したとき、項目側の転記済みは維持する（利用者が個別に外す）。
- 【変更提案】従属関係を仕様で明記する。もしくは §7 の提案どおり項目単位を初版から外す。

#### M. 案件IDの一意性と 8.2.6 の警告の強度（曖昧）

- 6.4 の ProjectGroup は `projectGroupId`（内部）と `projectId`（利用者入力）を持ち、`projectId` の一意制約は書かれていない。8.2.6 は「同一案件IDへ異なる対象種別を登録しようとした場合は**警告する**」とあり、禁止ではない。つまり同一 `projectId` で対象種別の異なる ProjectGroup が複数できる余地がある。その場合、12.1 のツリーで案件IDノードの下に対象種別の異なる実施回が混在し、8.2.5 の累計・残数をどの単位で集計するかが決まらない。
- 【暫定解釈】`projectId` は一意とし、8.2.6 の警告は「既存案件と対象種別が異なる」ことを知らせた上で、続行時は既存 ProjectGroup の対象種別を更新するのではなく新規作成を中止する。累計・残数は ProjectGroup 単位で集計する。
- 【変更提案】`projectId` の一意性と、警告後に続行できるかどうかを明記する。

#### N. 状態「集計済み」の成立契機（曖昧）

- 7.1 は「作業中 → 集計済み: 全作業項目に未終了区間がない」とする。条件が満たされた瞬間に自動遷移するのか、利用者操作が必要なのかが読み取れない。逆方向は「集計済み → 作業中: 確認操作を行う」と明示的に操作を要求している。
- 【暫定解釈】自動遷移させず、利用者が「集計済みにする」操作を行う。条件を満たさない場合はボタンを非活性とする（8.9.6）。
- 【変更提案】操作契機を明記する。

#### O. 転記値のクリップボード形式が未定義（不足）

- 8.7.7（推奨）はコピー機能を求めるが、形式（項目単位／実施回全体、区切り文字、外部コードを含むか）を定めていない。
- 【暫定解釈】外部項目コード順に `外部項目コード<TAB>転記値分` の行を並べたテキストとする（表計算へ貼り付けやすい）。
- 【変更提案】形式を明記する。CSV出力は 17章で将来候補とされているため、初版はクリップボードのみに留める。

#### P. 外部項目コード順の並び規則が未定義（不足）

- 8.7.3 は「外部項目コードがある場合、その順序で一覧表示できる」とあるが、コードは文字列であり、辞書順か自然順（数値部分を数値として比較）かで結果が変わる（例: `X-2` と `X-10`）。未設定項目の位置も未定義。
- 【暫定解釈】自然順（数値部分を数値比較）で昇順、未設定は末尾へ置き 8.7.4 の警告を付す。
- 【変更提案】並び規則を明記する。

#### Q. `schemaVersion` の二重管理（軽微）

- `schemaVersion` は Settings（6.2）とエクスポートJSON（9.2）の両方に現れる。値の生成元がどちらかが未定義。
- 【暫定解釈】`src/config.js` の定数を単一の正とし、Settings とエクスポートの両方へその値を書く。インポート時は JSON 側の値を検証対象とする（9.3）。

#### R. 未終了区間の合計秒・転記値の表示内容（不足）

- 8.6.5 は「未終了区間を含む作業項目の転記値は未確定として表示する」と定める。未確定時に、確定済み区間だけの小計を併せて表示するかは未定義。実施回合計をどう扱うかも同様。
- 【暫定解釈】確定済み区間と直接入力の小計は表示し、転記値は「未確定」と明示する（例: `4800秒（未確定・進行中1件）`）。実施回合計も同様に未確定を明示する。

#### S. インポート時の `schemaVersion` 不一致の扱い（曖昧）

- 9.3 は「`schemaVersion` を検証する」とし、A-12 は「スキーマ不一致のJSONを取り込んでも既存データが変更されない」ことを求める。初版は単一バージョンのため一致のみ許すのが自然だが、明記はない。
- 【暫定解釈】現行 `schemaVersion` と完全一致しない場合は取り込みを中止する（マイグレーションは行わない。データ移行は「同一バージョン間」と 13章が定める）。

#### T. 未終了しきい値の判定基準時刻（軽微）

- 8.8.2 は「開始から設定しきい値を超えた未終了区間を強調表示する」。基準は「現在日時 − `startAt`」と読めるが明記はない。再描画の頻度も未定義。
- 【暫定解釈】現在日時との差で判定し、1分ごとに再評価する。

## 8. テスト方針

### 8.1 方針の骨子

1. **計算は純関数の単体テストで固定する。** 工数計算・丸め・状態判定・検証は `domain/` の純関数に閉じ込め、UIを経由せずに網羅する。受入試験15件のうち計算系5件（T-04〜T-07、T-13）は単体テストで先に固定し、E2Eでも再確認する。
2. **保存はアダプター差し替えでテストする。** `StorageAdapter`（5.3）が定義済みのため、`MemoryAdapter` と `fake-indexeddb` で結合テストを行う。テストのために本番構造を曲げる必要がない。
3. **受入試験 T-01〜T-15 はE2Eで自動化する。** 仕様16章の試験表をそのままテストIDにし、追跡可能にする。
4. **外部通信ゼロ（13章、A-15）はテストで機械的に検証する。** E2Eでネットワーク要求を全遮断し、要求が発生したら失敗させる。
5. **架空データのみを使う（14章）。** フィクスチャは `対象種別A`／`参加者甲` 等の抽象名に限定し、実在の組織名・製品名・工程名を含めない。

### 8.3 実行環境と依存

【変更提案】§4.3 のとおり、開発時のみ Node ツールを使う。`mise.toml` に node 24 が既にあるため追加設定は不要。

```text
npm test          → Vitest（unit + integration）
npm run test:e2e  → Playwright（Chromium、静的配信を自動起動）
```

- 依存はすべて devDependencies。実行時の依存は増やさない（5.1.4）。
- Playwright のブラウザは配布物へ含めない。
- ライセンスは MIT / BSD / Apache-2.0 のものに限る（14章）。Vitest（MIT）、Playwright（Apache-2.0）、fake-indexeddb（Apache-2.0）はいずれも適合する。

**代替案（開発時依存を一切置かない場合）**: `tests/runner.html` にブラウザ上で動く簡易テストランナーを自作し、`domain/` の単体テストのみ自動化する。結合・E2Eは手動チェックリスト（16章の試験表）で代替する。この場合、T-11／T-12／T-14 のような回帰しやすい項目が手動になるため、品質維持のコストは上がる。**推奨は §4.3 の案。**

### 8.4 テストの受入基準

| 段階 | 基準 |
| ---- | ---- |

### 8.5 テストしない範囲

- 将来候補（17章）。
