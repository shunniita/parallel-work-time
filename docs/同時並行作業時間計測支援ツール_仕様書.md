## 1. 文書の目的

本書は、複数の案件、複数の作業項目、複数の参加者が同時並行で作業する状況において、作業時間と参加人数から項目別の総工数を記録・集計するブラウザアプリケーションの仕様を定める。

本ツールは、利用者が最終的な記録先へ数値を転記するまでの、一時的な記録・計算・確認を支援するものである。正式な勤怠管理、給与計算、原価計算、業務実績保管を代替するものではない。

## 2. 背景

一般的な時間計測ツールは、一人が一つの作業を順番に進める運用を前提とする場合が多い。

実際の作業現場では、次のような状況が発生する。

- 複数の案件が同時に進行する。
- 一つの案件に複数の作業項目がある。
- 複数人が同じ作業項目へ同時に参加する。
- 参加者が途中で増減する。
- 作業と休憩を複数回繰り返す。
- 作業中に正確な時刻を記録できず、後から工数のみを追加する。
- 同一案件を複数回に分けて実施する。

本ツールは、これらを一つの画面で記録し、最終的に「どの実施回の、どの作業項目に、合計何分の工数が掛かったか」を確認できるようにする。

## 3. 適用範囲

### 3.1 初版の対象

- 対象種別ごとに、必要な作業項目をテンプレートとして定義できる業務。
- 同一案件を複数の実施回へ分けて進める業務。
- 作業時刻または工数の直接入力から、項目別工数を求める用途。
- 一人の管理者が、一つの端末および一つのブラウザプロファイルから利用する運用。
- 外部システムへ手作業で転記するための集計支援。

### 3.2 初版の対象外

- 複数利用者による同時編集。
- 複数端末間の自動同期。
- サーバー側APIおよびサーバー側データベース。
- 認証、権限管理、承認ワークフロー。
- 勤怠、給与、請求、法定帳票への直接利用。
- 外部システムへの自動入力。
- 特注案件ごとの自由な工程設計。
- 作業者別の生産性評価。
- スマートフォン専用UI。
- 外部クラウドサービスおよび外部APIとの通信。

## 4. 用語

| 用語             | 定義                                                                       |
| ---------------- | -------------------------------------------------------------------------- |
| 案件ID           | 利用者が管理対象へ割り当てる識別子。同一案件IDの下に複数の実施回を持てる。 |
| 対象種別         | 作業対象の分類。製品、業務種別、イベント種別などを想定する。               |
| バリエーション   | 同一対象種別における仕様差。必要な作業項目の組合せを決める。               |
| 総予定数         | 案件全体で予定される数量。                                                 |
| 実施回           | 同一案件を分割して実施する単位。同じ日でも複数作成できる。                 |
| 今回数量         | 一つの実施回で扱う数量。                                                   |
| 作業項目         | 工数を集計する単位。                                                       |
| 作業テンプレート | 対象種別とバリエーションに対応する作業項目の定義。                         |
| 参加者           | 作業区間へ参加した人物。補助情報として文字列で保持する。                   |
| 作業区間         | 開始日時と終了日時を持つ作業または休憩の時間帯。                           |
| 直接入力         | 時刻を用いず、工数を直接追加する記録。                                     |
| 工数             | 作業時間と参加人数を掛けた合計作業時間。内部単位は秒。                     |
| 転記値           | 外部の記録先へ入力するため、工程合計秒を分単位へ切り上げた値。             |
| 外部項目コード   | 外部システムや帳票上の項目と対応付ける任意のコード。                       |
| アーカイブ       | 転記済みの実施回を、利用者の操作によって通常一覧から分離して保持する状態。 |
| 参加者変更       | 進行中の作業区間を指定時刻で終了し、新しい参加者一覧で同種別の区間を同時刻から開始する操作。 |

## 5. システム構成

### 5.1 実行形態

| #     | 要件                                                                             | 区分 |
| ----- | -------------------------------------------------------------------------------- | ---- |
| 5.1.1 | HTML、CSS、JavaScriptで構成する静的Webアプリとする。                             | 必須 |
| 5.1.2 | サーバー側プログラムおよびサーバー側DBを必要としない。                           | 必須 |
| 5.1.3 | HTTPまたはHTTPSで静的配信して利用する。`file://`での直接起動は動作保証外とする。 | 必須 |
| 5.1.4 | CDN、外部フォント、外部APIを利用しない。必要な資材はリポジトリへ同梱する。       | 必須 |
| 5.1.5 | ビルド工程を設けず、配布ZIPを展開して静的配信できる構成とする。Windows 11向け配布物には、外部ランタイムの追加インストールや管理者権限なしで起動できるローカル起動機能を同梱する。ローカル配信はループバックのみに限定し、既定URLを `http://127.0.0.1:4173/` とする。利用者は同梱の設定ファイルでポートを明示的・永続的に変更できる。ポート使用中は保存元URLを自動変更せず理由を示して失敗する。 | 必須 |

### 5.2 保存方式

| 対象                   | 保存先           | 備考                                     |
| ---------------------- | ---------------- | ---------------------------------------- |
| 案件、実施回、作業記録 | IndexedDB        | 操作後に即時保存                         |
| 作業テンプレート       | IndexedDB        | 初回起動時にサンプルJSONから初期投入可能 |
| 設定                   | IndexedDB        | 保持期間、警告しきい値など               |
| 簡易変更履歴           | IndexedDB        | 第11章に定める操作のみ                   |
| 外部バックアップ       | JSONファイル     | 利用者が明示的にエクスポート             |
| サンプルデータ         | リポジトリ内JSON | 架空データのみ                           |

### 5.3 保存処理の分離

保存処理は`StorageAdapter`を介して呼び出し、画面処理および計算処理からIndexedDB APIを直接呼び出さない。

初版の実装は`IndexedDbAdapter`とする。将来、共有サーバー、ローカルファイル、別のブラウザストレージへ移行する場合は、保存アダプターの差し替えで対応できる構造とする。

最低限、次の操作を定義する。

```text
initialize()
loadAll()
saveEntity(type, entity)
deleteEntity(type, id)
exportAll()
importAll(data)
```

### 5.4 Git管理

- プログラム、文書、架空のサンプルデータ、初期テンプレートをGitで管理する。
- 実際の案件データ、参加者名、エクスポートJSONはGit管理しない。
- `.gitignore`に、少なくとも次を登録する。

```gitignore
work-data_*.json
parallel-work-time_*.json
export/
*.local.json
*.private.json
```

`parallel-work-time_*.json`は、第9.2項が定めるエクスポート既定ファイル名に対応する。

## 6. データ構造

### 6.1 内部識別子

案件グループ、実施回、作業項目実績、作業区間、直接入力には、利用者が入力するIDとは別に内部固有IDを付与する。

内部固有IDは`crypto.randomUUID()`で生成する。

### 6.2 設定

```text
Settings
├─ schemaVersion
├─ retentionDays
├─ longRunningThresholdHours
└─ lastExportedAt
```

`schemaVersion`の値の正はソース上の設定定数（`config.js`）とする。`Settings`およびエクスポートJSONへは、その定数の値を書き込む。

### 6.3 作業テンプレート

```text
TaskTemplate
├─ templateSeriesId
├─ templateId
├─ targetType
├─ variant
├─ version
├─ active
├─ createdAt
└─ tasks[]
   ├─ taskDefinitionId
   ├─ name
   ├─ externalCode
   ├─ order
   └─ active
```

テンプレート改訂時は版番号を繰り上げ、旧版を保持する。

`templateSeriesId`は版系列を表す識別子であり、改訂しても変わらない。`templateId`は各版に固有の識別子であり、改訂ごとに新規発行する。同一系列の版は`templateSeriesId`で辿る。

旧版のレコードは保持するが、旧版を閲覧・比較する専用画面は初版では設けない。

実施回作成時には、その時点の作業項目定義を実施回側へ値として複製する。後からテンプレートを改訂しても、既存の実施回は変化させない。

### 6.4 案件グループ

```text
ProjectGroup
├─ projectGroupId
├─ projectId
├─ targetType
├─ variant
├─ totalQuantity
├─ createdAt
└─ updatedAt
```

### 6.5 実施回

```text
WorkRun
├─ runId
├─ projectGroupId
├─ workDate
├─ runQuantity
├─ status
├─ templateId
├─ templateVersion
├─ createdAt
├─ updatedAt
├─ transferredAt
├─ archivedAt
└─ tasks[]
```

`status`は`作業中`、`集計済み`、`転記済み`、`アーカイブ`のいずれかを保持する。`削除候補`は保存せず、`アーカイブ`かつ保持期間を経過した状態として現在日時から導出する。

`archivedAt`はアーカイブへ移動した日時であり、保持期間の起算日として用いる。アーカイブ前は`null`とする。

### 6.6 作業項目実績

```text
TaskRecord
├─ taskRecordId
├─ taskDefinitionId
├─ name
├─ externalCode
├─ order
├─ manuallyAdded
├─ intervals[]
└─ directEntries[]
```

転記済み状態は実施回単位でのみ管理する。作業項目単位の転記済みは保存しない（第8.7.5項）。

### 6.7 作業区間

```text
TimeInterval
├─ intervalId
├─ type: "work" | "break"
├─ startAt
├─ endAt
├─ participants[]
├─ createdAt
└─ updatedAt
```

`participants`は文字列配列とする。作業者マスターは設けない。

`endAt`が`null`の区間を未終了区間とする。

### 6.8 直接入力

```text
DirectEntry
├─ entryId
├─ seconds
├─ participants[]
├─ note
├─ createdAt
└─ updatedAt
```

直接入力は既存工数への加算とし、集計値の上書きには使用しない。

`seconds`は、すでに参加人数を含んだ総工数とする。集計時に参加者数を掛けない。`participants`は照合用の補助情報として保持する。

例えば2人がそれぞれ20分作業したことが後から判明した場合、入力する値は40分である。

## 7. 状態

実施回は次の状態を持つ。

| 状態       | 説明                                       | 保持方法 |
| ---------- | ------------------------------------------ | -------- |
| 作業中     | 工数を入力・修正できる。                   | `status`へ保存 |
| 集計済み   | 未終了区間がなく、転記値を確認できる。     | `status`へ保存 |
| 転記済み   | 外部の正式な記録先への入力が完了した。     | `status`へ保存 |
| アーカイブ | 転記済みとして通常一覧から分離されている。 | `status`へ保存 |
| 削除候補   | 保持期間を経過し、手動削除できる。         | 保存しない。現在日時から導出する派生状態 |

### 7.1 状態遷移

| 遷移                  | 条件                                     |
| --------------------- | ---------------------------------------- |
| 新規 → 作業中         | 実施回作成時                             |
| 作業中 → 集計済み     | 全作業項目に未終了区間がなく、かつ利用者が集計済みへの変更操作を行う。条件成立による自動遷移は行わない |
| 集計済み → 作業中     | 確認操作を行う                           |
| 集計済み → 転記済み   | 転記完了確認を行う                       |
| 転記済み → 集計済み   | 警告確認後に状態を戻す                   |
| 転記済み → アーカイブ | 利用者がアーカイブ操作を行う。転記済みへの変更による自動アーカイブは行わない |
| アーカイブ → 削除候補 | `archivedAt`から保持期間を経過（派生判定） |
| 削除候補 → 完全削除   | 利用者が確認して削除                     |

状態の進行は次のとおりであり、転記済みからアーカイブへは必ず利用者の操作を要する。

```text
集計済み
  ↓ 転記完了確認
転記済み
  ↓ 利用者のアーカイブ操作
アーカイブ
  ↓ archivedAtから保持期間経過
削除候補
```

転記済みの実施回は、状態を集計済み以下へ戻さない限り、工数を編集できない。

集計済みの実施回は工数を編集できる。ただし集計済みは「未終了区間がない」状態であるため、未終了区間を生成する操作（作業開始など）を行う場合は、利用者の確認後に実施回を作業中へ戻してから実行する。状態の変更と区間の生成は同一の保存処理で行い、確認しない場合はどちらも行わない。

終了済みの区間の修正、区間の手動追加、直接入力の追加・修正は、未終了区間を生じないため集計済みのまま行える。

### 7.2 作業項目の状態

作業項目の状態は保存せず、区間の内容から導出する派生値とする。

| 状態   | 判定条件                             |
| ------ | ------------------------------------ |
| 未着手 | 作業区間が存在しない                 |
| 作業中 | `type="work"`の未終了区間が存在する  |
| 休憩中 | `type="break"`の未終了区間が存在する |
| 完了   | 作業区間が存在し、未終了区間がない   |

`完了`は不可逆の状態ではない。未終了区間が存在しないことを表すのみであり、再び作業を開始すれば`作業中`へ戻る。

実施回が転記済みまたはアーカイブの場合、作業項目は閲覧のみとする。

### 8.4 時刻入力

| 8.4.9 | 複数の作業項目を同時に作業中の状態にできる。                         | 必須 |
| 8.4.10 | 作業中または休憩中に参加者を変更でき、変更時刻で区間を分割できる。   | 必須 |
| 8.4.11 | 後からの実績修正のため、作業区間を手動で追加できる。                 | 必須 |

#### 補足1 進行中区間の個数（第8.4.9項、第8.4.11項）

ボタン操作（開始、休憩、再開、終了）によって生じる未終了区間は、作業項目ごとに一つまでとする。

参加者が増減した場合は、区間を並行して追加せず、第8.4.10項の参加者変更によって区間を分割する。

一方、第8.4.11項の手動追加および第8.4.5項の編集では、同一作業項目内で時間帯が重複する区間を作成できる。これは、別のグループが同じ作業項目を実際に同時並行で実施した場合を表現できるようにするためである。重複時は第8.9.5項により警告するが、保存は禁止しない。

#### 補足2 参加者変更の処理（第8.4.10項）

作業中または休憩中に「参加者変更」を実行した場合、次の処理を行う。

1. 進行中の区間を指定時刻で終了する。
2. 新しい参加者一覧を選択する。
3. 同じ区間種別の区間を、同じ時刻から開始する。

指定時刻の初期値は現在日時とする。作業中であれば新しい作業区間を、休憩中であれば新しい休憩区間を開始する。これにより、休憩中に一部の参加者だけが作業へ戻る場合も記録できる。

記録例を次に示す。9時に甲・乙・丙で開始し、9時20分に丙が離脱した場合は次のようになる。

```text
09:00～09:20　甲、乙、丙
09:20～継続中　甲、乙
```

9時に甲・乙で開始し、9時30分に丙が参加した場合は次のようになる。

```text
09:00～09:30　甲、乙
09:30～継続中　甲、乙、丙
```

| 8.5.2 | 直接入力は時刻入力分へ加算する。                 | 必須 |

```text

```

### 8.6 工数計算

作業区間の工数は、次の方法で算出する。

```text
作業区間秒 =
    floor((終了日時 - 開始日時) / 1000)
    × 参加者数
```

休憩区間の工数は0秒とする。

```text
作業項目合計秒 =
    作業区間秒の合計
    + 直接入力秒の合計
```

```text
転記値分 =
    ceil(作業項目合計秒 / 60)
```

| #     | 要件                                                                 | 区分 |
| ----- | -------------------------------------------------------------------- | ---- |
| 8.6.1 | 日時差をミリ秒で計算し、秒へ切り捨ててから参加人数を掛ける。         | 必須 |
| 8.6.2 | 休憩区間を工数へ含めない。                                           | 必須 |
| 8.6.3 | 時刻入力分と直接入力分を秒単位で加算する。                           | 必須 |
| 8.6.4 | 各区間では丸めず、作業項目の合計に対して一度だけ分単位へ切り上げる。 | 必須 |
| 8.6.5 | 未終了区間を含む作業項目の転記値は未確定として表示する。             | 必須 |
| 8.6.6 | 直接入力秒には参加者数を掛けない（第8.5.6項）。                      | 必須 |

未終了区間を含む場合も、終了済み区間と直接入力から求めた確定分の小計は表示する。転記値のみを未確定として示す。実施回合計についても同様とする。

### 8.7 集計・転記支援

| #     | 要件                                                 | 区分 |


### 8.9 入力検証

| #     | 検証内容                                                                             | 区分 |
| ----- | ------------------------------------------------------------------------------------ | ---- |
| 8.9.1 | 案件ID、対象種別、バリエーション、総予定数、今回数量を必須とする。                   | 必須 |
| 8.9.2 | 数量は1以上の整数とする。                                                            | 必須 |
| 8.9.3 | 終了日時は開始日時以降とする。同一日時は0秒として許可する。                          | 必須 |
| 8.9.4 | `type="work"`の区間は参加者が0人の場合、保存を禁止する。`type="break"`の区間は0人を許可する。 | 必須 |
| 8.9.5 | 同一作業項目内で作業区間が重複する場合は警告する。保存は禁止しない。                 | 必須 |
| 8.9.6 | 未終了区間がある実施回は集計済みに変更できない。                                     | 必須 |
| 8.9.7 | 今回数量の累計が総予定数を超える場合は警告し、確認後に続行できる。                   | 必須 |
| 8.9.8 | 同一作業項目、同一参加者、同一秒数の直接入力が存在する場合は重複候補として警告する。 | 推奨 |
| 8.9.9 | 参加者名の表記ゆれは警告せず、利用者の判断に委ねる。                                 | 必須 |
| 8.9.10 | 整数入力は安全整数の範囲で判定し、運用上の上限を併せて設ける。                      | 必須 |
| 8.9.11 | JSONインポートは、通常の書き込み経路が保存する形の値だけを受理する。                | 必須 |
| 8.9.12 | 派生する合計工数にも上限を設ける。作業項目実績1件および実施回1件の合計秒が上限を超える入力は、保存も取り込みも受け付けない。 | 必須 |

「休憩」ボタンによって休憩区間を開始する場合は、直前の作業区間の参加者一覧を引き継いで設定する。利用者による追加入力を求めない。

8.9.10 の上限は、値が丸められたまま整数として受理されることを防ぐために設ける。`9007199254740993` のような値は変換の時点で別の値になり、入力した値と保存された値が一致しなくなる。上限そのものはソース修正なしで変更できる箇所へ置く（13章）。

8.9.11 は、案件ID・対象種別・バリエーション・作業項目名・外部項目コード・備考・理由が対象である。通常の入力は保存の直前に前後空白を落とすため、前後空白付きの値は画面から作れない。取り込みで受理すると、検索や一意性判定が正規化済みの入力と保存済みの生値を比べることになり、取り込んだデータを画面から引けなくなる。黙って正規化せず、場所を添えて拒否する。識別子は形を問わないが、長さは他の文字列と同じ上限に収める。

8.9.12 は、1件ずつの値の上限では防げない。工数は「経過秒 × 参加者数」を足し合わせた値であり、区間数・作業項目数・参加者数がそれぞれ上限内でも、積と和を重ねれば安全整数を超える。超えた時点で加算は丸められ、集計値と転記値が厳密値から静かにずれる。集計と転記は「厳密な秒の合計」であることが意味の前提なので、範囲外は値として認めない。

### 8.10 同一データの複数タブ利用

初版は同時編集に対応しない。

同一ブラウザプロファイルで複数タブから本ツールを開いた場合は、`BroadcastChannel`などを利用して検知し、次の警告を表示する。

```text
同じデータを別のタブでも開いています。
同時操作すると、後から保存した内容で上書きされる可能性があります。
```

複数タブを技術的に強制終了またはロックする必要はない。

## 9. 保存・バックアップ

### 9.1 自動保存

- 作成、編集、削除、状態変更の操作完了後にIndexedDBへ保存する。
- 保存成功または失敗を画面上へ表示する。
- 一連の関連書き込みは可能な範囲で同一トランザクションにまとめる。
- `QuotaExceededError`を捕捉し、JSONエクスポートと不要データ削除を促す。

### 9.2 JSONエクスポート

全データを一つのJSONファイルとして出力できる。

ファイル名は次の形式とする。

```text
parallel-work-time_YYYYMMDD-HHmmss.json
```

エクスポートJSONは次を含む。

```text
schemaVersion
exportedAt
settings
taskTemplates
projectGroups
workRuns
changeHistory
```

### 9.3 JSONインポート

- JSONファイルを選択して全データを取り込める。
- 初版では差分マージを行わず、全置換とする。
- 実行前に確認を表示する。
- JSON構文、`schemaVersion`、必須項目を検証する。
- `schemaVersion`が現行の値と一致しない場合は取り込みを拒否する。初版ではデータ移行処理を行わない。
- 検証に失敗した場合、既存データを一切変更しない。
- 置換前の既存データを自動ダウンロードできる導線を設ける。これは推奨要件とする。
- 取り込みの対象は、利用者本人が管理する信頼済みJSONとする。ファイルサイズ、コレクションごとの件数、文字列長、参加者数に上限を設け、超えるものは取り込む前に拒否する。
- 通常の生成経路では作れない構造は取り込まない。同一実施回内で同じ作業項目定義が2行現れるJSONはその一例であり、受理すると集計・転記の一覧へ同じ作業項目が重複して並ぶ。
- 本ツールが書き出したJSONは、同一バージョンへ必ず取り込める。この往復保証を成立させるため、書き込み時刻は関連する既存の日時より前にならない実効時刻を用いる。取り込み側の時系列検証は緩めない。
- 利用者の1回の操作意図に対して、全置換は1回だけ実行する。処理中は取り込みの操作を受け付けない。

### 9.4 破壊的操作前の退避

v2仕様にあった「保存操作のたびの全体スナップショット」は初版では採用しない。

IndexedDB内へ世代管理されたスナップショットを保持する方式も、初版では採用しない。第9.2項のJSONエクスポートと第9.3項のインポートが復旧手段として機能するためである。

次の破壊的操作の直前には、全データをJSONへ退避する導線を表示する。退避処理は共通の1機能とし、各操作から呼び出す。

- 全データインポート。
- 実施回または案件グループの削除。
- アーカイブデータの完全削除。

退避を行わずに続行することも選択できるが、その場合は取り消しできない旨を確認として表示する。

### 9.5 定期エクスポートの推奨

IndexedDBは端末、ブラウザ、オリジン単位で分離され、ブラウザデータの削除で失われる。

READMEおよび画面上で、定期的なJSONエクスポートを案内する。エクスポート頻度は利用者が決めるものとし、毎日の実施を必須とはしない。

## 11. 変更履歴

全面的な監査ログは初版では設けない。

次の情報を各データへ保持する。

```text
createdAt
updatedAt
```

簡易変更履歴を保持する操作は、次に限る。

- 転記済み状態からの後退。
- 作業区間または直接入力の削除。
- 実施回または案件グループの削除。

総予定数の変更、今回数量の変更、テンプレートの改訂については、初版では履歴を残さない。テンプレートの改訂は版番号と旧版レコードで追跡できるためである。

簡易変更履歴は次を持つ。

```text
historyId
timestamp
entityType
targetId
operation
summary
reason
```

`entityType`は履歴対象のデータ種別を表す。第4章の「対象種別」（`targetType`）とは別の概念である。

`reason`は、転記済み状態からの後退および削除の場合に必須とする。

変更前後の完全なオブジェクト複製は必須としない。

簡易変更履歴は第9.2項のエクスポート対象へ含める。

### 12.4 操作ボタン

現在状態に応じて、次のうち有効な操作だけを活性化する。

```text
開始
休憩
再開
終了
参加者変更
直接入力
履歴編集
区間追加
```

第7.2項の作業項目状態と操作の対応を次に示す。

| 状態                 | 可能な操作                                          |
| -------------------- | --------------------------------------------------- |
| 未着手               | 開始、直接入力、区間追加                            |
| 作業中               | 休憩、終了、参加者変更、直接入力、履歴編集、区間追加 |
| 休憩中               | 再開、終了、参加者変更、直接入力、履歴編集、区間追加 |
| 完了                 | 開始、直接入力、履歴編集、区間追加                  |
| 転記済み・アーカイブ | 閲覧のみ                                            |

各ボタンの処理は次のとおりとする。いずれも日時の初期値は現在日時とし、確定前に修正できる。

| 操作       | 処理                                                                     |
| ---------- | ------------------------------------------------------------------------ |
| 開始       | `type="work"`の区間を、終了日時なしで作成する。                          |
| 休憩       | 進行中の作業区間を指定時刻で終了し、同時刻から`type="break"`の区間を開始する。参加者は直前の作業区間から引き継ぐ。 |
| 再開       | 進行中の休憩区間を指定時刻で終了し、同時刻から`type="work"`の区間を開始する。 |
| 終了       | 進行中の区間を指定時刻で終了する。新しい区間は作成しない。               |
| 参加者変更 | 第8.4.10項の処理を行う。進行中の区間を指定時刻で終了し、新しい参加者一覧で同種別の区間を同時刻から開始する。 |
| 直接入力   | 第8.5項の直接入力を追加する。                                            |
| 履歴編集   | 既存の作業区間を修正・削除する。                                         |
| 区間追加   | 第8.4.11項により、開始日時と終了日時を指定して区間を手動追加する。       |

複数作業項目は独立して操作できる。

直接入力の修正・削除は「履歴編集」に含めない。直接入力一覧の各行から、常時行えるものとする。ただし実施回が転記済みまたはアーカイブの場合は閲覧のみとする（第7.2項）。

上表の「履歴編集」は未着手では無効である。作業区間が1件も存在しない状態であり、修正・削除の対象が無いためである。一方、直接入力は全状態で追加できるため、「作業区間は無いが直接入力だけがある作業項目」が生じる。この作業項目でも直接入力を修正・削除できる必要があるため、両者を同じ操作にまとめない。

削除にあたっては、第11章により理由の入力を必須とし、変更履歴へ記録する。

| 可搬性           | 静的ファイル一式を単一フォルダまたはZIPで配布できる。配布ZIPの作成は、実行環境の外部コマンドに依存せず、同じ入力から同じバイト列を出す。 |
| 保守性           | 作業テンプレート、保持期間、警告しきい値、入力値の上限をソース修正なしで変更できる。   |
| データ移行       | JSONエクスポートとインポートにより、同一バージョン間で移行できる。                     |
| 性能             | 案件20件、実施回100件、作業区間2,000件程度で通常操作に支障がないことを初版の目標とする。これを超える規模の保証は行わず、測定した実測値をREADMEへ記載する。 |
| セキュリティ     | 入力データを外部へ送信しない。                                                         |
| アクセシビリティ | マウス操作だけでなく、主要入力欄をキーボードで移動できる。                             |
| 表示             | タブレットで最適化しないが、狭い画面でも操作不能な崩壊を避ける。                       |

## 14. ライセンスと公開要件

- 公開リポジトリへ、実在する組織名、製品名、工程名、案件ID、参加者名、実績データを含めない。
- サンプルデータはすべて架空とする。
- 自作部分のライセンスをリポジトリ直下の`LICENSE`へ明示する。
- 外部ライブラリを利用する場合は、MIT、BSD、Apache-2.0のいずれかを原則とする。
- 外部ライブラリのライセンス文を`licenses`ディレクトリへ同梱する。
- AGPLおよび用途制限付きライセンスの依存関係は初版では採用しない。
- GitHub Releasesへ、ビルド不要の配布ZIPを添付できる構成を推奨する。
