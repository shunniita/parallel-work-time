## 1. 文書の目的

本書は、複数の案件、複数の作業項目、複数の参加者が同時並行で作業する状況において、作業時間と参加人数から項目別の総工数を記録・集計するブラウザアプリケーションの仕様を定める。

本ツールは、利用者が最終的な記録先へ数値を転記するまでの、一時的な記録・計算・確認を支援するものである。正式な勤怠管理、給与計算、原価計算、業務実績保管を代替するものではない。

## 2. 背景

一般的な時間計測ツールは、一人が一つの作業を順番に進める運用を前提とする場合が多い。

実際の作業現場では、次のような状況が発生する。

- 複数の案件が同時に進行する。
- 一つの案件に複数の作業項目がある。
- 複数人が同じ作業項目へ同時に参加する。
- 参加者が途中で増減する。
- 作業と休憩を複数回繰り返す。
- 作業中に正確な時刻を記録できず、後から工数のみを追加する。
- 同一案件を複数回に分けて実施する。

本ツールは、これらを一つの画面で記録し、最終的に「どの実施回の、どの作業項目に、合計何分の工数が掛かったか」を確認できるようにする。

## 3. 適用範囲

### 3.1 初版の対象

- 対象種別ごとに、必要な作業項目をテンプレートとして定義できる業務。
- 同一案件を複数の実施回へ分けて進める業務。
- 作業時刻または工数の直接入力から、項目別工数を求める用途。
- 一人の管理者が、一つの端末および一つのブラウザプロファイルから利用する運用。
- 外部システムへ手作業で転記するための集計支援。

### 3.2 初版の対象外

- 複数利用者による同時編集。
- 複数端末間の自動同期。
- サーバー側APIおよびサーバー側データベース。
- 認証、権限管理、承認ワークフロー。
- 勤怠、給与、請求、法定帳票への直接利用。
- 外部システムへの自動入力。
- 特注案件ごとの自由な工程設計。
- 作業者別の生産性評価。
- スマートフォン専用UI。
- 外部クラウドサービスおよび外部APIとの通信。

## 4. 用語

| 用語             | 定義                                                                       |
| ---------------- | -------------------------------------------------------------------------- |
| 案件ID           | 利用者が管理対象へ割り当てる識別子。同一案件IDの下に複数の実施回を持てる。 |
| 対象種別         | 作業対象の分類。製品、業務種別、イベント種別などを想定する。               |
| バリエーション   | 同一対象種別における仕様差。必要な作業項目の組合せを決める。               |
| 総予定数         | 案件全体で予定される数量。                                                 |
| 実施回           | 同一案件を分割して実施する単位。同じ日でも複数作成できる。                 |
| 今回数量         | 一つの実施回で扱う数量。                                                   |
| 作業項目         | 工数を集計する単位。                                                       |
| 作業テンプレート | 対象種別とバリエーションに対応する作業項目の定義。                         |
| 参加者           | 作業区間へ参加した人物。補助情報として文字列で保持する。                   |
| 作業区間         | 開始日時と終了日時を持つ作業または休憩の時間帯。                           |
| 直接入力         | 時刻を用いず、工数を直接追加する記録。                                     |
| 工数             | 作業時間と参加人数を掛けた合計作業時間。内部単位は秒。                     |
| 転記値           | 外部の記録先へ入力するため、工程合計秒を分単位へ切り上げた値。             |
| 外部項目コード   | 外部システムや帳票上の項目と対応付ける任意のコード。                       |
| アーカイブ       | 転記済みの実施回を通常一覧から分離して保持する状態。                       |

## 5. システム構成

### 5.1 実行形態

| #     | 要件                                                                             | 区分 |
| ----- | -------------------------------------------------------------------------------- | ---- |
| 5.1.1 | HTML、CSS、JavaScriptで構成する静的Webアプリとする。                             | 必須 |
| 5.1.2 | サーバー側プログラムおよびサーバー側DBを必要としない。                           | 必須 |
| 5.1.3 | HTTPまたはHTTPSで静的配信して利用する。`file://`での直接起動は動作保証外とする。 | 必須 |
| 5.1.4 | CDN、外部フォント、外部APIを利用しない。必要な資材はリポジトリへ同梱する。       | 必須 |
| 5.1.5 | ビルド工程を設けず、配布ZIPを展開して静的配信できる構成を推奨する。              | 推奨 |

### 5.2 保存方式

| 対象                   | 保存先           | 備考                                     |
| ---------------------- | ---------------- | ---------------------------------------- |
| 案件、実施回、作業記録 | IndexedDB        | 操作後に即時保存                         |
| 作業テンプレート       | IndexedDB        | 初回起動時にサンプルJSONから初期投入可能 |
| 設定                   | IndexedDB        | 保持期間、警告しきい値など               |
| 外部バックアップ       | JSONファイル     | 利用者が明示的にエクスポート             |
| サンプルデータ         | リポジトリ内JSON | 架空データのみ                           |

### 5.3 保存処理の分離

保存処理は`StorageAdapter`を介して呼び出し、画面処理および計算処理からIndexedDB APIを直接呼び出さない。

初版の実装は`IndexedDbAdapter`とする。将来、共有サーバー、ローカルファイル、別のブラウザストレージへ移行する場合は、保存アダプターの差し替えで対応できる構造とする。

最低限、次の操作を定義する。

```text
initialize()
loadAll()
saveEntity(type, entity)
deleteEntity(type, id)
exportAll()
importAll(data)
```

### 5.4 Git管理

- プログラム、文書、架空のサンプルデータ、初期テンプレートをGitで管理する。
- 実際の案件データ、参加者名、エクスポートJSONはGit管理しない。
- `.gitignore`に、少なくとも次を登録する。

```gitignore
work-data_*.json
export/
*.local.json
*.private.json
```

## 6. データ構造

### 6.1 内部識別子

案件グループ、実施回、作業項目実績、作業区間、直接入力には、利用者が入力するIDとは別に内部固有IDを付与する。

内部固有IDは`crypto.randomUUID()`で生成する。

### 6.2 設定

```text
Settings
├─ schemaVersion
├─ retentionDays
├─ longRunningThresholdHours
└─ lastExportedAt
```

### 6.3 作業テンプレート

```text
TaskTemplate
├─ templateId
├─ targetType
├─ variant
├─ version
├─ active
├─ createdAt
└─ tasks[]
   ├─ taskDefinitionId
   ├─ name
   ├─ externalCode
   ├─ order
   └─ active
```

テンプレート改訂時は版番号を繰り上げ、旧版を保持する。

実施回作成時には、その時点の作業項目定義を実施回側へ値として複製する。後からテンプレートを改訂しても、既存の実施回は変化させない。

### 6.4 案件グループ

```text
ProjectGroup
├─ projectGroupId
├─ projectId
├─ targetType
├─ variant
├─ totalQuantity
├─ createdAt
└─ updatedAt
```

### 6.5 実施回

```text
WorkRun
├─ runId
├─ projectGroupId
├─ workDate
├─ runQuantity
├─ status
├─ templateId
├─ templateVersion
├─ createdAt
├─ updatedAt
├─ transferredAt
└─ tasks[]
```

### 6.6 作業項目実績

```text
TaskRecord
├─ taskRecordId
├─ taskDefinitionId
├─ name
├─ externalCode
├─ order
├─ manuallyAdded
├─ transferred
├─ intervals[]
└─ directEntries[]
```

### 6.7 作業区間

```text
TimeInterval
├─ intervalId
├─ type: "work" | "break"
├─ startAt
├─ endAt
├─ participants[]
├─ createdAt
└─ updatedAt
```

`participants`は文字列配列とする。作業者マスターは設けない。

### 6.8 直接入力

```text
DirectEntry
├─ entryId
├─ seconds
├─ participants[]
├─ note
├─ createdAt
└─ updatedAt
```

直接入力は既存工数への加算とし、集計値の上書きには使用しない。

## 7. 状態

実施回は次の状態を持つ。

| 状態       | 説明                                       |
| ---------- | ------------------------------------------ |
| 作業中     | 工数を入力・修正できる。                   |
| 集計済み   | 未終了区間がなく、転記値を確認できる。     |
| 転記済み   | 外部の正式な記録先への入力が完了した。     |
| アーカイブ | 転記済みとして通常一覧から分離されている。 |
| 削除候補   | 保持期間を経過し、手動削除できる。         |

### 7.1 状態遷移

| 遷移                  | 条件                                     |
| --------------------- | ---------------------------------------- |
| 新規 → 作業中         | 実施回作成時                             |
| 作業中 → 集計済み     | 全作業項目に未終了区間がない             |
| 集計済み → 作業中     | 確認操作を行う                           |
| 集計済み → 転記済み   | 転記完了確認を行う                       |
| 転記済み → 集計済み   | 警告確認後に状態を戻す                   |
| 転記済み → アーカイブ | 転記済みに変更した時点、または利用者操作 |
| アーカイブ → 削除候補 | 保持期間を経過                           |
| 削除候補 → 完全削除   | 利用者が確認して削除                     |

転記済みの実施回は、状態を集計済み以下へ戻さない限り、工数を編集できない。

### 8.6 工数計算

作業区間の工数は、次の方法で算出する。

```text
作業区間秒 =
    floor((終了日時 - 開始日時) / 1000)
    × 参加者数
```

休憩区間の工数は0秒とする。

```text
作業項目合計秒 =
    作業区間秒の合計
    + 直接入力秒の合計
```

```text
転記値分 =
    ceil(作業項目合計秒 / 60)
```

### 8.10 同一データの複数タブ利用

初版は同時編集に対応しない。

同一ブラウザプロファイルで複数タブから本ツールを開いた場合は、`BroadcastChannel`などを利用して検知し、次の警告を表示する。

```text
同じデータを別のタブでも開いています。
同時操作すると、後から保存した内容で上書きされる可能性があります。
```

複数タブを技術的に強制終了またはロックする必要はない。

## 9. 保存・バックアップ

### 9.1 自動保存

- 作成、編集、削除、状態変更の操作完了後にIndexedDBへ保存する。
- 保存成功または失敗を画面上へ表示する。
- 一連の関連書き込みは可能な範囲で同一トランザクションにまとめる。
- `QuotaExceededError`を捕捉し、JSONエクスポートと不要データ削除を促す。

### 9.2 JSONエクスポート

全データを一つのJSONファイルとして出力できる。

ファイル名は次の形式とする。

```text
parallel-work-time_YYYYMMDD-HHmmss.json
```

エクスポートJSONは次を含む。

```text
schemaVersion
exportedAt
settings
taskTemplates
projectGroups
workRuns
```

### 9.3 JSONインポート

- JSONファイルを選択して全データを取り込める。
- 初版では差分マージを行わず、全置換とする。
- 実行前に確認を表示する。
- JSON構文、`schemaVersion`、必須項目を検証する。
- 検証に失敗した場合、既存データを一切変更しない。
- 置換前の既存データを自動ダウンロードできる導線を設ける。これは推奨要件とする。

### 9.4 スナップショット

v2仕様にあった「保存操作のたびの全体スナップショット」は初版では採用しない。

次の破壊的操作の直前に限り、IndexedDB内へスナップショットを作成する。

- 全データインポート。
- 実施回または案件グループの削除。
- アーカイブデータの完全削除。
- スナップショットからの復元。

直近3世代を保持する。

### 9.5 定期エクスポートの推奨

IndexedDBは端末、ブラウザ、オリジン単位で分離され、ブラウザデータの削除で失われる。

READMEおよび画面上で、定期的なJSONエクスポートを案内する。エクスポート頻度は利用者が決めるものとし、毎日の実施を必須とはしない。

## 10. データ保持・削除

| #    | 要件                                               | 区分 |
| ---- | -------------------------------------------------- | ---- |
| 10.1 | 転記済みの実施回をアーカイブへ移動できる。         | 必須 |
| 10.2 | 初期保持期間は30日とし、設定で変更できる。         | 必須 |
| 10.3 | 保持期間を経過した実施回を削除候補として表示する。 | 必須 |
| 10.4 | 完全削除は利用者の確認操作によってのみ行う。       | 必須 |
| 10.5 | 完全削除前に対象データをJSONとして保存できる。     | 推奨 |
| 10.6 | 無確認の自動削除は行わない。                       | 必須 |

## 11. 変更履歴

全面的な監査ログは初版では設けない。

次の情報を各データへ保持する。

```text
createdAt
updatedAt
```

次の操作については、簡易変更履歴を保持する。

- 総予定数の変更。
- 今回数量の変更。
- 転記済み状態からの後退。
- 作業区間または直接入力の削除。
- テンプレートの改訂。

簡易変更履歴は次を持つ。

```text
historyId
timestamp
targetType
targetId
operation
summary
reason
```

変更前後の完全なオブジェクト複製は必須としない。

## 12. 画面要件

### 12.1 基本レイアウト

画面幅1280px以上のPCを主対象とする。

左側に階層一覧、右側に選択中の詳細を表示する二分割構成を基本とする。

```text
案件ID
└─ 実施回
   └─ 作業項目
```

### 12.2 画面一覧

| 画面               | 内容                                                             |
| ------------------ | ---------------------------------------------------------------- |
| 案件・実施回一覧   | 案件ID、実施回、作業項目をツリー表示する。                       |
| 案件・実施回登録   | 案件ID、対象種別、バリエーション、数量、作業日を入力する。       |
| 作業項目詳細       | 時刻履歴、直接入力、参加者、工数内訳を表示・編集する。           |
| 集計・転記         | 実施回ごとの転記値を一覧表示する。                               |
| 作業テンプレート   | 対象種別、バリエーション、作業項目を登録・改訂する。             |
| アーカイブ         | 転記済み、削除候補を表示する。                                   |
| 設定・バックアップ | 保持期間、異常しきい値、JSON入出力、スナップショット復元を扱う。 |

未終了区間と異常候補は、専用画面を必須とせず、案件一覧上部の固定警告領域および絞り込み表示で確認できればよい。

### 12.3 作業項目行

各作業項目について、次を一行で確認できるようにする。

```text
作業項目名
外部項目コード
現在状態
時刻入力分
直接入力分
転記値
転記済み状態
```

### 12.4 操作ボタン

現在状態に応じて、次のうち有効な操作だけを活性化する。

```text
開始
休憩
再開
終了
直接入力
履歴編集
```

複数作業項目は独立して操作できる。

## 13. 非機能要件

| 項目             | 要件                                                                                   |
| ---------------- | -------------------------------------------------------------------------------------- |
| 動作環境         | 最新安定版のChromium系ブラウザを主対象とする。                                         |
| 通信             | 外部通信を行わない。                                                                   |
| 可搬性           | 静的ファイル一式を単一フォルダまたはZIPで配布できる。                                  |
| 保守性           | 作業テンプレート、保持期間、警告しきい値をソース修正なしで変更できる。                 |
| データ移行       | JSONエクスポートとインポートにより、同一バージョン間で移行できる。                     |
| 性能             | 案件100件、実施回1,000件、作業区間20,000件程度で通常操作に支障がないことを目標とする。 |
| セキュリティ     | 入力データを外部へ送信しない。                                                         |
| アクセシビリティ | マウス操作だけでなく、主要入力欄をキーボードで移動できる。                             |
| 表示             | タブレットで最適化しないが、狭い画面でも操作不能な崩壊を避ける。                       |

## 14. ライセンスと公開要件

- 公開リポジトリへ、実在する組織名、製品名、工程名、案件ID、参加者名、実績データを含めない。
- サンプルデータはすべて架空とする。
- 自作部分のライセンスをリポジトリ直下の`LICENSE`へ明示する。
- 外部ライブラリを利用する場合は、MIT、BSD、Apache-2.0のいずれかを原則とする。
- 外部ライブラリのライセンス文を`licenses`ディレクトリへ同梱する。
- AGPLおよび用途制限付きライセンスの依存関係は初版では採用しない。
- GitHub Releasesへ、ビルド不要の配布ZIPを添付できる構成を推奨する。
