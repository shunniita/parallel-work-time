### 1.1 採番は全件で数える（D-14）

**決定: 「第n回」はアーカイブ済みも含めた全件を通して振り、絞り込みは採番の後に行う。**

表示中のものだけを数えると、第1回をアーカイブした瞬間に第2回が「第1回」へ繰り上がる。利用者は「第2回の分を転記した」のように番号で記録を指すため、後から番号が動くと過去のやり取りと突き合わせられない。

アーカイブは「通常一覧から分離する」操作であって（10.1）、記録を無かったことにする操作ではない。数量の累計にアーカイブ済みを含める（8.2.5）のと同じ考え方である。

あわせて案件詳細の実施回一覧からアーカイブ済みを外した。これまで累計用の全件配列をそのまま描いており、10.1 に反していた。

## 2. 仕様が決めていない点の決定

### 2.1 削除できるのは削除候補だけ（仕様が決めている）

これは決定事項ではなく、仕様書7.1 の遷移表がそのまま定めている。

```text
アーカイブ → 削除候補 → 完全削除
```

アーカイブ済みから完全削除へ向かう辺は無い。したがって**削除候補であることが完全削除の事前条件**である。保持期間は「削除を勧める目安」ではなく「削除できるようになるまでの保護期間」として働く。

10.3 の「削除候補として**表示する**」を表示だけの要件と読み、保持期間内でも削除できると解釈することもできるが、その読みは7.1 の遷移表と両立しない。完全削除は取り消せないため、表示要件の解釈で安全条件を緩める判断はしない。

誤って作った実施回をすぐ消したい場合は、保持期間の設定を短くする（10.2）。設定は利用者が変えられるため、仕様の枠内に逃げ道がある。

判定は `retention.js` の `canDeleteRun()` に置き、画面のボタン制御と保存の事前条件で共有する。押せるかどうかと保存が通るかどうかを別々に書くと、押せたのに失敗する（またはその逆の）状態ができる。保存側でも再判定するのは、保持期間の経過が時間で変わり、画面を描いた時点と押した時点で結果が変わりうるためである。

### 2.2 案件の削除は配下がすべて削除候補のときだけ

仕様書10.4 は「完全削除は利用者の確認操作によってのみ行う」としか書かず、案件グループの削除条件を定めていない。

**決定: 配下の実施回がすべて削除候補である場合に限り、案件を削除できる。**

1件ずつ消せない記録を、案件ごとならまとめて消せるという抜け道を作らない。§2.1 の条件を案件単位でも保つ形である。

**実施回が0件の案件は条件を満たす。** 消える記録が無いので、保持期間が守る対象も無い。これは登録しただけで使わなかった案件や、最後の実施回を消した案件を削除する唯一の経路でもある（§2.8）。

### 2.3 案件削除の履歴は1件だけ

案件を消すと配下の実施回もまとめて消える。実施回1件ずつの履歴は残さず、案件グループの履歴1件へまとめる。

利用者から見て「案件を消す」という**1つの操作**であり、複数の削除ではない。消えた規模は要約へ件数と累計数量で残す。

### 2.4 理由と退避は別々に尋ねる

完全削除には2つの確認が要る。理由の入力（11章）と、退避の有無（10.5、9.4）である。

**決定: 1つの画面へ混ぜず、理由 → 退避の順に2段で尋ねる。**

理由は「なぜ消すか」、退避は「消す前に控えを取るか」であり、利用者が答える問いが違う。1つのフォームへ並べると、退避を選ばずに理由だけ書いて確定できてしまう形になりやすい。

退避の処理は `io/safetyExport.js` の `runDestructiveAction()` で、Step 9 のインポート全置換と共通である。

### 2.5 アーカイブに変更履歴は残さない

仕様書11章が記録を求めるのは「転記済み状態からの後退」と「削除」である。アーカイブはどちらでもない。記録は残ったままで、通常一覧から分離するだけである。

`archivedAt` が残るため、いつ分離したかは実施回自身が持つ。

### 2.6 アーカイブからは戻れない

仕様書7.1 の遷移表に「アーカイブ → 何か」の辺が無い。`TRANSITIONS` でもアーカイブからの遷移を空にした。

戻す必要があるなら、そもそも分離していない。誤ってアーカイブした場合は、退避したJSONから取り込み直す（9.3）。

### 2.7 残り日数は切り上げ、保持期限ちょうどは候補に含める

「あと n 日」の n は切り上げる。残り0.5日を「あと0日」と出すと、今日中に消えるように読める。

**決定: 保持期限ちょうどの時点を削除候補に含める。** 保持期間30日は「30日間保つ」であり、30日が満了した瞬間に保つ義務は終わる。

判定と表示は同じ数から導く。`isDeletable()` と `daysUntilDeletable()` が別々の比較を持つと、境界のちょうど1点で「残り0日と出ているのに候補ではない」という説明できない状態ができる。両方とも残り時間（ミリ秒）を求める1つの内部関数を見ており、`daysUntilDeletable()` が0を返すことと `isDeletable()` が真であることは一致する。

### 2.8 実施回が0件の案件もアーカイブ画面へ出す

アーカイブ済みの実施回から案件を逆引きすると、実施回が1件も無い案件は一覧に現れない。ところが案件削除を呼べる画面はここしかないため、最後の実施回を消した案件や、登録しただけで使わなかった案件が、通常操作では二度と消せなくなる。

**決定: アーカイブ済みが1件以上ある案件に加えて、実施回が0件の案件も一覧へ出す。**

アーカイブ済みが0件で運用中の実施回だけを持つ案件は出さない。アーカイブ画面へ出す意味が無く、削除もできない。

最後の実施回を消したときに案件を暗黙で削除する方法は採らない。案件削除に必要な理由の入力と変更履歴を省くことになる（11章）。

### 2.9 設定値に上限を設ける

仕様書は保持期間としきい値の上限を定めていない。

**決定: 保持期間は3650日、未終了しきい値は8760時間を上限とする。**

これらの値は日時の加算へそのまま入る。上限が無いと `1e20` のような値を保存でき、加算結果が `Date` の表現範囲を超えて `NaN` になる。`NaN` は比較で例外になるため、保存済みの設定が原因でアーカイブ画面が開けなくなる。入力の時点で弾く方が復旧しやすい。

上限は保存の入口、スキーマ検証、JSON取り込み検証が同じ述語（`config.js` の `isSettingInRange()`）を使う。読み取り側は既定値へ倒す（`resolveRetentionDays()`）。範囲外の値が何らかの経路で保存済みになっても、画面が開けなくなるより既定値で動く方がよい。

## 3. 保存層への追加

### 3.1 `saveEntities()` が削除を扱えるようにした

削除と変更履歴は同時に成立しなければならない（11章）。片方だけが残ると、消えたのに履歴が無いか、履歴だけあって記録が残る。どちらも後から機械的に直せない。

これまで一括操作は保存だけを扱っていたため、`{type, entity, remove: true}` を受け付けるよう広げた。案件削除では「配下の実施回すべて＋案件＋履歴1件」を1回の書き込みへまとめる。途中で失敗すると、案件だけ消えて実施回が親を失う——`integrity.js` が取り込みで拒む形のデータが、保存済みに生じてしまう。

削除でも `entity` を渡すのは、主キーの取り出しを保存と同じ経路にするためと、呼び出し側が「何を消したか」を手元に持っている状態で渡すためである（削除履歴の要約に要る）。

設定（`settings`）は削除できない。`deleteEntity()` と同じ扱いにした。
