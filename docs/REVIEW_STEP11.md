## 1. 指摘

### S11-1 BFCacheから復帰すると多重タブ警告が片側だけ消える

- 重要度: **Major**（複数タブが再び操作可能になっても、片側でA-13の警告が成立しない）
- 対象: `src/app/tabGuard.js:72-78`、`tests/unit/tabGuard.test.js:50-82`、`tests/e2e/warnings.spec.js:39-55`

`tabGuard.js` は、すべての `pagehide` で `bye` を送る。`pagehide` はページの破棄時だけでなく、ブラウザがページをBFCacheへ退避するときにも発生する。退避中のページは操作できないため、その時点で相手から外すこと自体は妥当である。

しかし、BFCacheからの復帰時に発生する `pageshow` を処理しておらず、`hello` を再送しない。タブBが退避した時点でタブAはBを `peers` から削除するが、Bの復帰後もAがBを知り直す契機がない。

偽チャンネルと `pagehide({ persisted: true })` / `pageshow({ persisted: true })` を使った最小再現では、次の結果になった。

```text
2タブ起動後       peerCount = [1, 1]
タブBをBFCacheへ  peerCount = [0, 1]
タブBを復帰       peerCount = [0, 1]
pageshow handler              = 無し
```

B自身はAを記憶したままなので警告を出すが、Aの警告は消えたままになる。その後Aへ戻って操作しても再検知されず、Bとの後勝ち保存が起こりうる。

現在のT-14は次の操作列だけを検査する。

```text
1タブ目を開く → 2タブ目を開く → 両方で警告 → 2タブ目を閉じる
```

このため「閉じずに別ページへ移動し、履歴から復帰する」という状態寿命の違いを検出しない。

`pagehide` では従来どおり `bye` を送り、`pageshow` の `event.persisted === true` で `hello` を再送する。単体テストへ上記の操作列を追加し、可能なら実ブラウザでもBFCache復帰後に両側の警告が再表示されることを確認する。

- 推奨対応時期: Step 11 の完了を宣言する前
- 状況: **対応済み**。`pageshow` の `persisted` で `hello` を送り直す。あわせて退避時（`persisted` な `pagehide`）に自分の記憶も捨てるようにした。止まっているあいだに相手が閉じても `bye` を受け取れないため、復帰直後の記憶は当てにならない。`pagehide` / `pageshow` の発生源を差し替え可能にし、単体テストで片方のタブだけを退避させて指摘の操作列を固定した（6件）。実ブラウザでも「別ページへ移って戻る」E2E を追加した。

### S11-2 ARIAツリー上で親子関係が成立していない

- 重要度: **Minor**（見た目は3階層でも、支援技術が親子階層を正しく取得できない）
- 対象: `src/ui/tree.js:241-267,280-311`、`tests/unit/ui/tree.test.js:510-521`

展開されたツリーのDOMは、概略として次の構造になる。

```text
li role="none"
├─ div
│  └─ button role="treeitem"
└─ ul role="group"
```

`role="group"` は親 `treeitem` の子ではなく、`role="none"` の `li` の下で兄弟要素になっている。`aria-owns` も無いため、ARIA上は「このgroupがどのtreeitemの子か」という所有関係が成立しない。

実際のDOMを調べた結果も、案件配下と実施回配下の両方で次のとおりだった。

```text
group.parentElement.role = none
groupを所有するtreeitem = 無し
```

WAI-ARIA Tree View Patternは、親ノードの `treeitem` が子ノードを包む `group` を包含または所有することを求める。現在の単体テストは `tree` / `group` / `treeitem` がそれぞれ存在することだけを数えるため、関係の誤りを検出しない。

DOM構造を親 `treeitem` が `group` を含む形へ変更するか、親 `treeitem` と対応する `group` を一意なIDと `aria-owns` で結ぶ。試験もroleの個数ではなく、各groupが正しい親treeitemに包含または所有されることを確認する。

- 推奨対応時期: D-18を対応済みとするStep 11内
- 状況: **対応済み**（`aria-owns`）。`treeitem` は `button` なので子の `ul` を内側へ置けず、DOM 構造の変更は採らなかった。畳んでいるあいだは `ul` が無いため `aria-owns` も付けない。試験は role の個数ではなく、各 group に所有者の treeitem が居ることと、案件・実施回それぞれの所有先を確かめる形にした。

### S11-3 1つの選択に3件の `aria-current` が立つ

- 重要度: **Minor**（選択中の作業項目ではなく祖先案件がTabの停留所になる）
- 対象: `src/ui/tree.js:179-190,202-250,271-294`、`tests/unit/ui/tree.test.js:267-295,421-434`

作業項目を選ぶと、画面状態の `selection` には案件・実施回・作業項目のIDがすべて入る。各ノードは自分のIDだけを比較して `current` を決めるため、同じ選択経路上の3要素がすべて `aria-current="true"` になる。

選択済みの3階層を実測した結果は次のとおりである。

```text
案件       aria-current=true  tabindex=0
実施回     aria-current=true  tabindex=-1
作業項目   aria-current=true  tabindex=-1
```

`applyRovingTabindex()` は最初に見つかった `aria-current="true"` をTabの停留所にするため、選択中の作業項目ではなく案件を選ぶ。警告領域のリンクなど、ツリー外から作業項目を開いた後にTabでツリーへ入ると、表示中の詳細と停留所が一致しない。

WAI-ARIA 1.2は、関連する1セットの中で `aria-current` を付ける要素を1つにすることを推奨する。最深部の選択だけをcurrentにするか、単一選択ツリーとして `aria-selected` を使用する。少なくとも「作業項目選択時にcurrentが1件で、その項目の `tabindex` が0」という試験を追加する。

- 推奨対応時期: D-18を対応済みとするStep 11内
- 状況: **対応済み**（最深部のみ current）。判定を `currentKeyOf()` へ集約し、各段は自分のキーと突き合わせるだけにした。3か所の条件式に分けたままだと、片方だけ直したときに一意性が崩れる。見た目の選択表示も同じ判定に合わせ、ARIA と食い違わないようにした。「作業項目選択時に current が1件で、その項目の `tabindex` が0」を試験で固定した。

### S11-4 `onblocked` で拒否した後に未管理のDB接続が開く

- 重要度: **Minor**（接続を1つに集約するC-13の目的に反し、`close()`できない接続が残る）
- 対象: `src/storage/IndexedDbAdapter.js:117-152,408-413`、`tests/integration/storageAdapter.contract.test.js:738-782`

`openDatabase()` は `onblocked` でPromiseをrejectし、利用者へ「ほかのタブを閉じてから再読み込み」と返す。しかし、Promiseのrejectは `IDBOpenDBRequest` を取り消さない。ブロックしている旧接続が後から閉じると、同じ要求の `onsuccess` が遅れて発生する。

旧版の生接続で版2へのopenを塞いだ最小再現では、次の結果になった。

```text
initialize()の結果      = blockedでreject
旧接続を閉じた後のイベント = blocked → success
adapter.db              = null
```

`onsuccess` で得た接続は、既にreject済みのPromiseへ `resolve()` されるため呼び出し元へ届かない。`adapter.db` にも保持されず、`adapter.close()` から閉じられない。C-13で防ごうとした「閉じられずに残る接続」が、ブロック解除後の遅延成功という別経路で発生する。

現在の契約テストは、管理中の接続が `onversionchange` で協調的に閉じる経路だけを確認するため、`onblocked` へ到達しない。

`onblocked` 後に遅れて `onsuccess` が発生した場合、`request.result.close()` して接続を破棄する。旧接続を意図的に保持してblockedを発生させ、解除後に未管理接続を残さない契約テストを追加する。

- 推奨対応時期: C-13を対応済みとするStep 11内
- 状況: **対応済み**。決着済みかどうかを覚えておき、遅れて成功した接続はその場で `close()` する。なお**指摘が挙げた「解除後に未管理接続を残さない」を、次の版上げが塞がれるかで観測すると検出できない**。C-13 で入れた `onversionchange` を残された接続も持つため、次の要求には協調して閉じてしまう。接続そのものが開いたままかを、トランザクションを開始できるか（閉じていれば `InvalidStateError`）で確かめる形にした。最初この観測点を誤って書き、修正を戻しても試験が通ってしまうことに気づいて直している。

### S11-5 マウスで折りたたみボタンを押すとフォーカスが消える

- 重要度: **Minor**（マウスで展開した直後に矢印キー操作へ移れない）
- 対象: `src/ui/tree.js:66-100,193-200`、`docs/STEP11_DESIGN.md:84-96`、`tests/e2e/warnings.spec.js:117-138`

折りたたみボタンはクリック時に `toggle()` を呼び、即座にツリー全体を再描画する。クリックされたボタン自身もDOMから削除される。

フォーカス中ノードの記録は `focusin` された要素から最寄りの `treeitem` を探すが、折りたたみボタンは `treeitem` の子ではなく兄弟である。そのためボタンをクリックしても `focusedKey` は更新されず、再描画後に新しいノードへ `focus()` する処理もない。結果としてフォーカスは `body` へ落ちる。

キーボードの左右矢印経路では、再描画後に `focusItem(key)` を呼ぶため問題が出ない。既存E2Eも案件treeitemへ先にフォーカスして矢印キーだけを使うため、マウスとキーボードを連続して使う操作を検出しない。

折りたたみボタンのクリック時にも対象treeitemのキーを保持し、再描画後にそのtreeitemへフォーカスを戻す。またはS11-2のARIA構造修正と合わせて、展開操作を親treeitemの操作へ統合する。

- 推奨対応時期: D-18を対応済みとするStep 11内
- 状況: **対応済み**。折りたたみボタンの押下時に対象 treeitem のキーを控え、再描画後にそこへフォーカスを戻す。ただし戻すのは押した時点でフォーカスがツリー内にあった場合だけとした。ツリー外で操作していた利用者からフォーカスを奪わないためである。

## 2. 成立を確認した契約

- 全実施回から未終了区間を収集し、案件・第n回・作業項目を添えて開始日時順に表示する。
- 転記済み・アーカイブ済みに残る異常な未終了区間も隠さず、「閲覧のみの実施回」と表示する。
- しきい値超過を保存せず、現在日時、開始日時、設定値から派生させる。
- 1分ごとの再評価では警告領域の文字列と強調だけを更新し、リンクのDOMとフォーカスを保つ。
- 未終了区間の集合が変わった場合だけ警告領域の構造を描き直す。
- 未終了区間、多重タブ、アプリ通知のいずれも無い場合は警告領域を畳む。
- 通常の2タブ起動では、先行タブと後発タブの双方が `hello` / `ack` で相手を検知する。
- 相手が通常終了して `bye` を送ると、多重タブ警告を解除する。
- 多重タブを検知しても操作をロックせず、仕様書8.10の警告文を表示する。
- 保存成否表示に `role="status"` と `aria-live="polite"` を付ける。
- ツリー内を上下左右、Home、Endで移動し、Tabの停留所を1件にする。
- 作業項目の状態記号を読み上げ対象から外し、状態名を `aria-label` に含める。
- 並行した `initialize()` を同じopen Promiseへ合流させる。
- 管理中のIndexedDB接続は `onversionchange` を受けると自分から閉じ、以後の操作を再読み込み案内付きで拒否する。
- サンプルテンプレートの読込失敗と捕捉されなかった実行時例外を、無言にせず警告領域へ表示する。

## 6. mino系スキルの適用判断

- `mino-reproducible-development`: 仕様、設計、実装、単体・結合・E2E、ブラウザAPIの状態寿命、最小再現を対応付けるため使用した。
- `mino-domain-model-completeness`: タブの起動・退避・復帰・終了、警告の表示・解除、ツリーの選択と階層、DB接続の管理主体という状態と遷移の欠落を確認するため使用した。
- `mino-design-by-contract`: 多重タブ検知の事前・事後条件、警告解除条件、roving tabindexの一意性、blocked後の失敗保証と接続解放を確認するため使用した。
- `mino-interface-implementation-separation`: 今回は公開操作と内部実装の責務境界より、状態寿命とアクセシビリティ契約が中心だったため使用しなかった。
- `mino-architecture-quality-strategy`: 複数システム間の正本、移行、回復方式を変更するレビューではなく、単一ブラウザアプリ内の警告・接続・UI契約で解決できるため使用しなかった。
