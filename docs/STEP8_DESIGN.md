## 2. 仕様が決めていない点の決定

### 2.1 実施回の転記値に2つの値を持たせる

仕様書8.6.5 は「未終了区間を含む作業項目の転記値は未確定として表示する」と定め、続けて「確定済み区間と直接入力から求めた確定分の小計は表示する。実施回合計についても同様とする」と書く。

つまり実施回の合計には**2つの意味**がある。混同すると転記の数字を誤るため、`aggregateRun()` は両方を別の名前で返す。

| 値 | 意味 | 未確定のとき |
| -- | ---- | ------------ |
| `transferMinutesSum` | 実施回全体が確定しているときの合計 | `null` |
| `confirmedTransferMinutesSum` | 確定済みの作業項目だけを足した小計 | 常に数値 |

`transferMinutesSum` が `null` のときに `confirmedTransferMinutesSum` を「実施回の転記値」として扱ってはならない。まだ記録されていない作業が残っている。画面は未確定のとき「未確定（進行中n件）。確定済みm件の小計はk分」と、小計であることを文言で明示する。

なお合計は**作業項目ごとに切り上げてから足す**（8.6.4、8.7.1）。実施回の合計秒をまとめて切り上げた値ではない。30秒×3項目は 1分×3＝3分であり、90秒→2分ではない。

### 2.2 コピーから除く行がある（8.7.7）

仕様書8.7.7 は形式（`外部項目コード<TAB>転記値分`）と並び（外部項目コード順）だけを定め、**出せない行の扱いを決めていない**。

**決定: 外部項目コード未設定の行と、転記値が未確定の行はコピーへ含めない。除いた件数は画面へ出す。**

| 除く対象 | 理由 |
| -------- | ---- |
| 外部項目コード未設定 | 貼り付け先はコードで行を突き合わせる。空のコードを混ぜると、外部システム側で行がずれるか取り込みが失敗する |
| 転記値が未確定 | 未終了区間を含む項目には転記値が無い（8.6.5）。仮の値を入れると、確定していない数字が正式な記録先へ入る |

「貼り付けたテキストがそのまま使える状態であること」を優先した。ただし**黙って落とさない**。コピー後の通知へ「外部項目コード未設定の1件は含めていません」のように件数と理由を必ず添える。除いた行は一覧では見えている。

### 2.3 クリップボードは2経路で試す

`navigator.clipboard.writeText()` は安全なコンテキスト（HTTPS または localhost）でしか使えない。本ツールは HTTP 配信も想定しており（5.1.3）、社内の素の HTTP なホストへ置くと `navigator.clipboard` 自体が存在しない。

**決定: `navigator.clipboard` → `document.execCommand('copy')` → 失敗の順に落とす。**

`execCommand` は非推奨だが、現在も主要ブラウザで動き、外部ライブラリを増やさずに済む（5.1.4）。どちらも使えない場合は `{ok: false, reason}` を返し、画面が「表の値を選択してコピーしてください」と案内する。例外にしないのは、コピーの失敗が記録の失敗ではなく、利用者が別の手段で回避できる事柄だからである。

### 2.4 転記の目印は実施回が変わったら捨てる

作業項目単位の転記済みは保存しない（8.7.5）。画面上の一時チェックとして提供する。

仕様は「再読み込みで消える」ことしか含意していないが、実装では**別の実施回を選んだ時点でも捨てる**。残っていると「どこまで転記したか」の目印として誤る。並べ替えでは捨てない（同じ実施回を見続けているため）。

一覧の下に「保存しないため、再読み込みすると消えます」と明記する。保存される印だと誤解されると、転記の管理をこれに頼ってしまう。

### 2.5 拒む理由を2つに分ける

「その遷移が許されているか」（7.1）と「記録の中身が揃っているか」（8.9.6）は別の問いである。

| 問い | 担当 | 例 |
| ---- | ---- | -- |
| 状態の図の上で辺があるか | `runStatus.js` の `canTransition()` | 作業中から転記済みへは飛べない |
| 記録の中身が揃っているか | `aggregate.js` の `canAggregate()` | 未終了区間が3件ある |

まとめて1つのエラーにすると、利用者は「なぜ進めないのか」を区別できない。作業中から集計済みへ進む場合だけ、両方を順に確かめる。画面はボタンの `title` へ理由を入れ、押してから初めて知る形にしない。

### 2.6 転記済みから戻すときは未終了区間を見ない

`canAggregate()` を通すのは**作業中から集計済みへ進むときだけ**である。転記済みから集計済みへ戻すときは確かめない。

既に集計済みだった記録であり、戻すこと自体を未終了区間の有無で拒む理由が無い。むしろ「戻して直す」ためにこの操作があるので、中身を理由に拒むと直す手段が無くなる。

### 2.7 転記完了日時は戻したら消す

`transferredAt`（6.5）は「いま転記済みであること」を表す値とする。転記済みから戻したら `null` へ戻す。

転記した事実そのものは変更履歴が残す（11章）。両方に持たせると、「`transferredAt` はあるが状態は集計済み」という読み方の定まらない組み合わせができる。

## 3. 状態遷移とガードの関係

`transferActions.js` は**状態ガード（`assertEditable()`）を通さない唯一のアクション群**である。

他のアクション（区間・直接入力・数量）はすべて `isRunEditable()` を通し、転記済み・アーカイブでは拒む（7.2）。ここだけは通さない。転記済みから集計済みへ戻す操作は、まさに「閲覧のみ」の状態から抜けるための操作であり、閲覧のみを理由に拒むと二度と戻せなくなる。

代わりに `canTransition()` が状態の図の上で辺があるかを見る。この例外は `runStatus.js` の冒頭に規約として書いてある。

### 3.1 Step 8 で実装した遷移

```text
作業中 ──[集計済みにする]──▶ 集計済み ──[転記完了確認]──▶ 転記済み
   ▲                            │                          │
   └──────[作業中へ戻す]────────┘                          │
                                ▲                          │
                                └──[理由必須・履歴あり]────┘
```

アーカイブと完全削除（10章）は Step 10 で `TRANSITIONS` へ足す。**自動遷移は行わない**（7.1、確認事項N）。未終了区間が無くなっても集計済みへは進まない。条件が揃うことと、利用者が「集計を終えた」と決めることは別である。

### 3.2 変更履歴（11章）

記録するのは**転記済みからの後退だけ**である。集計済み→作業中は記録しない。仕様書11章が求めているのは「転記済み状態からの後退」であり、集計済みは外部へ渡す前の状態だからである。

区間削除（Step 6）・直接入力削除（Step 7）と同じく、状態の書き換えと履歴1件を `saveEntities` で同一トランザクションへまとめる（9.1）。片方だけが残ると「戻した記録が無いのに集計済み」か「戻した履歴だけあって転記済みのまま」になる。どちらも後から機械的に直せない。

### 4.1 削除確認を「理由必須の確認」へ一般化した

転記済みの取り消しは削除ではないが、**理由必須・確定・取消・エラー表示・保存中の無効化**という作りが削除確認とまったく同じである。`deleteConfirm.js` を `reasonConfirm.js` へ改め、語（`action.verb` / `action.noun`）と `testid` の接頭辞を差し替えられるようにした。

既定値は従来の削除の文言と `testid` にしてあるため、区間・直接入力の呼び出し側とテストは変わらない。
