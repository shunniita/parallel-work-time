## 2. 指摘

### GAR-1 「退避してインポート」が一つの排他操作になっていない

- 重要度: **Major**
- Evidence: **confirmed**（実コードと反例プローブで再現）
- 影響要件: 仕様書9.1、9.3、9.4、A-11
- 対象:
  - `src/io/safetyExport.js:9-22`
  - `src/app/actions/settingsActions.js:57-96`
  - `src/app/persistence.js:61-157`
  - `src/ui/views/settingsView.js:97-109`

#### 観測

`runDestructiveAction()` は `exportData()` の完了を待ってから `destructiveAction()` を呼ぶ。しかし両者は別々の `persistence.run()` であり、待ち行列が保持する排他範囲は個々の保存操作だけである。

そのため、エクスポートの書き込み待ち中に別操作が保存キューへ入ると、順序は次のようになる。

```text
退避用エクスポート
  → 別操作の保存
  → 全置換インポート
```

別操作の保存内容は退避JSONの取得後に作られ、直後の全置換で消える。退避JSONにも置換後データにも残らない。

#### 実測した反例

1. `MemoryAdapter` の設定保存だけを保留させ、退避付きインポートを開始した。
2. 退避JSONの内容が確定した後、同じ `persistence` へテンプレート新規登録を積んだ。
3. 保留を解除し、エクスポート、テンプレート登録、インポートの順に完了させた。
4. テンプレート登録Promiseは成功したが、退避JSONのテンプレート件数も置換後の件数も0件だった。

```json
{"backupTemplates":0,"finalTemplates":0}
```

これは多重タブを使わず、同一タブの保存キューだけで再現する。設定画面の処理中もヘッダーナビゲーションは利用できるため、実画面から別操作へ移ることも禁止されていない。

#### 必要な契約

- 「退避して破壊的操作」を、一つの排他区間として扱う。
- 破壊的操作より前に受理した書き込みは、退避JSONへ含めるか、破壊的操作後に実行する。
- 退避にも置換後にも存在しない成功済み書き込みを作らない。
- 失敗時は全置換を実行せず、既存データを保持する。

#### 推奨対応

エクスポートと全置換を個別にキューへ積むのではなく、複合操作全体を `persistence` の排他単位にする。加えて、全置換処理中はヘッダーナビゲーションと全書き込み操作を止める。UIの無効化だけを唯一の防御にせず、保存境界側でも割り込み不能にする。

**状況**: **対応済み（2026-08-09）。** `persistence.runExclusive()` を新設し、退避と破壊的操作を1つの排他区間へ入れた。区間の内側かどうかを共有フラグで見分ける案は採らない。区間の実行中に利用者が別画面を操作した場合まで「内側」と誤判定し、まさに防ぎたい割り込みを許すためである。区間で使うアクションは呼び出し側が渡す形にし、画面は「何を壊すか」だけを決める。割り込んだ保存は失われず、置換後の内容へ載る（反例 ADV-01 を結合テストへ固定）。

### GAR-2 重複参加者を含むJSONが工数を水増しできる

- 重要度: **Major**
- Evidence: **confirmed**（整合性検証と集計を実行して再現）
- 影響要件: 仕様書8.6.1、8.9.4、8.9.9、9.3、A-05、A-07、A-11
- 対象:
  - `src/domain/schema.js:300-324`
  - `src/domain/integrity.js:335-343`
  - `src/domain/intervalOps.js:103-120`
  - `src/domain/effort.js:55-64`

#### 観測

通常入力は参加者名の前後空白を除き、空文字と完全一致の重複を除去する。一方、インポート検証は `participants` が文字列配列であることと、`work` 区間で配列長が1以上であることしか確認しない。

工数計算は `interval.participants.length` を人数として掛けるため、同じ名前を複数回入れたJSONは、同一人物を複数人として計上する。

#### 実測した反例

1時間の `work` 区間へ `participants: ["甲", "甲"]` を設定したJSONを検証した。

```json
{
  "validation": {"ok": true, "schemaMismatch": false, "errors": []},
  "totalSeconds": 7200
}
```

検証は成功し、本来3,600秒である同一人物1名の作業が7,200秒になった。この値は集計、分単位の切り上げ、コピー用転記値へ伝播する。

#### 必要な契約

- 参加者名は前後空白を除いた値で評価する。
- `work` 区間では、正規化後の参加者が1名以上必要である。
- 同一区間内の完全一致参加者を重複して保持しない。
- インポートを通したデータの人数解釈を、通常入力と一致させる。

#### 推奨対応

インポート時は黙って正規化せず、空白名または正規化後重複を場所つきエラーとして拒否する。インポートが全置換であることと、入力ファイルの誤りを利用者が直せることを優先する。

**状況**: **対応済み（2026-08-09）。** 空白名・正規化後の重複・作業区間の実質0人を、場所つきエラーとして拒否する。黙って正規化しない。全置換である以上、直す機会は取り込み前にしかない。直接入力にも同じ検査を通す（工数は変わらないが、重複候補の判定 8.9.8 が参加者一覧の一致で行われるため）。

### GAR-3 アーカイブ日時の前後関係を検証せず、保持期間を迂回できる

- 重要度: **Major**
- Evidence: **confirmed**（整合性検証と削除可否判定を実行して再現）
- 影響要件: 仕様書7.1、9.3、10.2、10.3、A-10、A-11
- 対象:
  - `src/domain/integrity.js:368-419`
  - `src/domain/retention.js:53-64`
  - `src/domain/schema.js:243-270`

#### 観測

整合性検証は、転記済みとアーカイブ済みに必要な日時が存在するかを確認するが、作成、更新、転記、アーカイブの前後関係を確認しない。保持期間判定は `archivedAt` を唯一の起算日としてそのまま使う。

#### 実測した反例

次のアーカイブ済み実施回を含むJSONを検証した。

```text
createdAt     = 2026-07-30T09:00:00+09:00
archivedAt    = 2020-01-01T00:00:00+09:00
transferredAt = 2099-01-01T00:00:00+09:00
```

結果は `validateImport().ok === true` であり、2026-08-08時点・保持期間30日で `canDeleteRun().ok === true` となった。作成前にアーカイブされ、アーカイブ後に転記されるという到達不能な時系列が、保持期間経過済みとして扱われる。

完全削除には利用者の再確認が残るため自動削除ではないが、「保持期間が残っている記録を保護する」という判定の根拠が成立しない。

#### 必要な契約

通常操作が生成するアーカイブ済み実施回について、少なくとも次を満たす。

```text
createdAt <= transferredAt <= archivedAt <= updatedAt
```

通常状態についても `createdAt <= updatedAt` を要求する。日時が同秒になることは許す。

#### 推奨対応

構造検証の後、`compareIso()` を使って状態日時の前後関係を整合性検証へ追加する。前後関係が壊れたJSONを自動補正すると保持期間の意味を変えるため、取り込み前に拒否して場所と理由を表示する。

**状況**: **対応済み（2026-08-09）。** `createdAt <= transferredAt <= archivedAt <= updatedAt` を整合性検証へ追加した。同秒は許す。自動補正はしない。日時を書き換えると保持期間の意味そのものが変わる。

### GAR-4 非同期処理の完了後、移動前のビューが共有ペインを上書きする

- 重要度: **Minor**
- Evidence: **confirmed**（DOM環境で再現）
- 影響要件: 仕様書12.1、12.2、13章
- 対象:
  - `src/main.js:349-386`
  - `src/main.js:442-445`
  - `src/ui/views/settingsView.js:53-79`
  - `src/ui/views/summaryView.js:114-132`
  - `src/ui/views/templateView.js:85-99`

#### 観測

各ビューは同じ `shell.detailPane` を描画先として共有する。非同期保存の完了後、ビューは自分が現在のビューかを確認せず、ローカルの `render()` を直接呼ぶ。

#### 実測した反例

設定画面でエクスポートを保留し、その間に詳細ペインを「別画面」へ置き換えた。エクスポートを完了させると、設定画面が再び詳細ペインを描画した。

```json
{"restoredSettings":true,"otherStillVisible":false}
```

実アプリではヘッダーの現在画面と詳細ペインが食い違う。状態変更操作の場合、別の実施回へ移動した後に、元の実施回へ対する成功通知を現在の選択へ表示する可能性もある。

#### 推奨対応

ビューまたはナビゲーションへ世代番号・所有権トークンを持たせ、非同期処理開始時と完了時で一致した場合だけ局所描画する。保存結果によるデータセット更新は従来どおりストア購読へ任せる。

**状況**: **対応済み（2026-08-09）。** 詳細ペインの所有者を `main.js` の `activeDetailKey()` で1か所に決め、各ビューは `isActive()` で自分の番かだけを見る。案件画面は選択の深さで中身が変わるため、`VIEW` の値ではなく専用の識別子を返す。

### GAR-5 インポート可能な識別子がツリーのDOM参照を壊す

- 重要度: **Minor**
- Evidence: **confirmed**（コード経路と入力契約の照合）
- 影響要件: 仕様書9.3、12.1、13章
- 対象:
  - `src/domain/schema.js:188-302`
  - `src/ui/tree.js:58-70`
  - `src/ui/tree.js:162-177`

#### 観測

JSON内の各識別子は非空文字列であればよい。ツリーの子グループIDは、キー内の `\w` と `-` 以外をすべて `-` へ置き換えて作る。そのため `a:b` と `a/b` のような別識別子が同じDOM IDになる。

またフォーカス復元では、識別子を `CSS.escape()` せず属性セレクターへ埋め込む。引用符や角括弧を含む識別子では、別要素への一致または `querySelector()` の `SyntaxError` が起こりうる。

内部生成IDはUUIDなので通常操作では到達しないが、同一バージョンJSONの取り込み契約はこれらの識別子を許可している。

#### 推奨対応

- DOM IDは衝突しない符号化または描画単位の採番で作る。
- 属性セレクターへ値を埋める場合は `CSS.escape()` を使う。
- より単純には、既に取得済みの `visibleItems()` から `dataset.treeKey` の完全一致で探す。

**状況**: **対応済み（2026-08-09）。** `aria-owns` のIDを識別子から組み立てず、描画ごとの連番にした。フォーカス復元は属性セレクターをやめ、取得済みの要素から `dataset.treeKey` の完全一致で探す。

### GAR-6 テンプレート改訂アクションから有効版の一意性を破れる

- 重要度: **Minor**
- Evidence: **confirmed**（アクション層を直接呼んで再現）
- 影響要件: 仕様書6.3、8.1.1、9.2、9.3
- 対象:
  - `src/app/actions/templateActions.js:94-136`
  - `src/domain/templateOps.js:39-68`
  - `src/domain/validation.js:105-130`

#### 観測

`reviseTemplateAction()` は対象種別とバリエーションを含む下書きを受け取り、`reviseTemplate()` もそれらの変更を許す。一方、同じ組み合わせの有効版が既に存在するかを調べる `validateTemplateIsNew()` は新規登録時にしか呼ばれない。

#### 実測した反例

「対象A / 標準」と「対象B / 標準」を登録後、対象Aの有効版を「対象B / 標準」へ改訂した。

```json
{
  "active": [
    ["対象B", "標準", 1],
    ["対象B", "標準", 2]
  ],
  "validation": {
    "ok": false,
    "errors": ["対象B / 標準 の有効版が2つ以上ある"]
  }
}
```

保存自体は成功するが、その直後に出力したJSONを同じアプリへ取り込めない。

現在の編集画面は対象種別とバリエーションを改訂欄に出していないため、通常UIからは到達しない。現時点では潜在欠陥だが、アクションの引数契約とドメイン関数は変更を許しており、将来画面へ出した時点で顕在化する。

#### 推奨対応

対象種別・バリエーションの変更を仕様として許すなら、改訂元自身を除いた有効版との衝突を検査する。変更を許さないなら、アクションとドメイン関数の契約から変更可能性を取り除き、保存済み値を常に引き継ぐ。

**状況**: **対応済み（2026-08-09、選択肢1）。** 改訂元自身を除いた有効版との衝突を検査する。対象種別の表記誤りを直せる余地は仕様書8.1.3 が禁じておらず、`reviseTemplate` の設計意図でもあるため残した。

## 4. 成立を確認した横断契約

- すべての通常保存アクションは `persistence.run()` を通り、同一タブ内の単一保存操作は直列化される。
- WorkRun本体と削除・後退の変更履歴は、`saveEntities()` により同一トランザクションへまとめられる。
- 転記済みからアーカイブへ進むとき、`transferredAt` を保持し `archivedAt` を追加する。
- アーカイブ済み実施回は通常ツリーから分離されるが、案件数量の累計と採番には残る。
- JSON全置換の `clear` と `put` は、IndexedDBの全ストアを含む一つのトランザクションで行われる。
- 取り込み拒否時は既存データを変更しない。
- 文字列表示はDOMノードの `textContent` 相当で組み立て、利用者入力をHTMLとして解釈しない。
- 通常の二タブとBFCache復帰後の多重タブ警告が成立する。

GAR-1は「単一の保存操作」の直列化を否定するものではない。二つの保存操作を一つの破壊的業務操作として扱う排他境界が無いことを指す。

## 9. 適用したレビュー観点

本レビューは、単一関数の正しさだけでなく、次の横断関係を検証した。

- 目的と要件から、保存・取り込み・削除・復旧の操作列へ往復できるか。
- source of truthであるIndexedDBへ到達するすべてのwriterが同じ不変条件を守るか。
- JSONという代替入力経路が、通常UIより弱い意味制約になっていないか。
- 単一保存の原子性だけでなく、利用者から一操作に見える複合処理が原子的か。
- 非同期処理完了時に、描画先の所有権が現在のビューと一致するか。
- 内部生成値では安全でも、公開境界で許可した値がDOM実装を壊さないか。

Architecture、domain completeness、contract、interface boundaryの各観点はこの横断検証へ統合し、個別の重複レポートは作成していない。
