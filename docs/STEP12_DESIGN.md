## 1. 着手前に済ませた敵対的レビュー対応

Step 11 完了後の全体レビュー（PWT-REVIEW-008）で挙がった6件を先に片付けた（コミット `3fee275`）。判断が分かれたものだけ記す。

### 1.1 排他区間は「渡す」形にする（GAR-1）

「退避してから全置換」は利用者から1つの操作に見えるが、保存は2回である。その隙間へ別の保存が入ると、退避JSONにも置換後にも残らない書き込みができる。

**決定: `persistence.runExclusive(body)` を足し、区間内で使う `run` を `body` へ渡す。**

共有フラグで「いま区間の内側か」を見分ける案は採らない。区間の実行中に利用者が別画面を操作した場合まで内側と誤判定し、まさに防ぎたい割り込みを許す。呼び出し元が明示的に受け取る形なら、外から積まれた保存は必ず待つ。

あわせて、破壊的操作の取引境界を画面から `main.js` へ移した。画面は「何を壊すか」だけを決め、退避と本体をどう束ねるかはアプリ層が持つ。

### 1.2 取り込みは黙って正規化しない（GAR-2、GAR-3）

参加者名の空白・重複と、状態日時の前後関係を、場所つきエラーとして拒否する。

**決定: 自動補正しない。** 全置換である以上、直す機会は取り込み前にしかない。参加者を黙って正規化すると「読み込ませた内容と保存された内容が違う」ことに気づけない。日時を書き換えると保持期間の意味そのものが変わる。

### 1.3 テンプレート改訂の対象種別変更は残す（GAR-6）

改訂で対象種別・バリエーションを直せる余地は残し、改訂元自身を除いた有効版との衝突だけを検査する。仕様書8.1.3 は変更を禁じておらず、表記の誤りを直せることには利点がある。

## 2. 受入試験の総仕上げ

### 2.1 試験IDを試験名の先頭へ置く

T-01〜T-18 のすべてを Chromium E2E で自動化し、試験名を `T-nn 内容（A-nn）` の形へ揃えた。`--grep "T-10"` で1本だけ実行できる。

これまで T-01・T-02 は「T-01相当」、T-09・T-11・T-12・T-18 は本文中の言及だけで、試験名から追えなかった。**追跡表を別に持つより、試験自身が名乗る方が食い違わない。**

### 2.2 T-04 を T-16 から分けた

数字はどちらも「20分×3人＋30分×2人＝120分」で同じだが、確かめるものが違う。

- **T-04（A-05）**: 参加者変更を挟まず、作業時間へ参加人数を掛けた値が積み上がること。
- **T-16（A-16）**: 参加者を変更すると変更時刻で区間が分割され、前後が別々に計算されること。

T-16 だけでも数値は出るが、それは分割が正しいことの結果である。掛け算そのものが壊れたときに落ちる試験を別に持つ。

### 2.3 手動確認を減らした

実装計画8.2 は5項目を手動確認としていた。うち3項目を自動化した。

| 対象 | 扱い |
| ---- | ---- |
| 狭い画面での崩壊回避（13章） | 自動化。`warnings.spec.js` が1024pxで段組みと横スクロール無しを見る |
| キーボード操作（13章） | Step 11 で自動化済み |
| 保存成否の表示（9.1） | 自動化。`statusBar.test.js` が状態ごとの表示を見る |
| 二分割レイアウト（12.1） | 手動のまま。見た目の良し悪しは判定できない。画像出力だけ自動 |
| 配布ZIP（14章） | 展開のみ手動。展開後と同一のディレクトリに対する起動・保存・エクスポートは自動 |

保存失敗の表示を実ブラウザでIndexedDBの書き込みを失敗させて見る案は採らない。状態を渡すだけで再現でき、手間に見合う情報が増えない。

## 3. viewport の判断（レビュー指摘 D-19）

`index.html` は `width=1280` で幅を固定し、`layout.css` は `max-width: 1279px` の狭幅対応を持っていた。固定した幅は常に1280なので、このメディアクエリは実機で発火しない。

**決定: `width=device-width, initial-scale=1` へ変え、狭幅対応を活かす。**

仕様書12.1 の「画面幅1280px以上のPCを主対象とする」は変わらない。一方13章は「狭い画面でも操作不能な崩壊を避ける」と定めており、幅を固定すると狭い画面で横スクロールしないと操作できない。主対象を広い画面に置くことと、狭い画面を壊さないことは両立する。

E2E で1440pxの2段組みと1024pxの1段組み、横スクロールが出ないことを固定した。

## 4. 性能の実測（仕様書13章）

### 4.1 生成はIndexedDBへ直接書く

画面操作で2,000区間を作ると試験だけで数十分かかる。測りたいのは「その規模のデータを抱えたときの描画・集計・出力」であって入力操作ではないため、保存済みの状態を直接組み立てる。

### 4.2 閾値は緩く、値は記録する

実行機の性能に左右されるので、合否は「明らかな破綻」（各操作5秒）だけを見る。READMEへ載せる数字は試験の出力から採る。

目標規模（案件20件・実施回100件・区間2,000件）での実測値は次のとおり。

| 操作 | 実測値 |
| ---- | ------ |
| 起動（全件読み込み＋左ツリー描画） | 約160ms |
| 実施回の集計表示 | 約53ms |
| JSONエクスポート | 約59ms |

敵対的レビュー 4.1（`loadAll()` の全件メモリロード）が懸念した規模の破綻は、目標規模では起きない。桁が変わる規模を保証しないことは仕様書13章が明示しており、READMEにも書いた。

## 5. 配布（仕様書14章、5.1.5）

### 5.1 含めるものを列挙する

`tools/build-dist.mjs` は、配布物へ含めるものを明示的に列挙して写す。除外リストではなく採用リストにしたのは、ファイルが増えたときに黙って混入しないためである。

```text
start-local.cmd / local-settings.txt / LICENSE / README.md / manual/
アプリ内部（変更しないでください）/
  _local-server.ps1 / index.html / src/ / data/ / licenses/
```

### 5.2 ZIP圧縮はOSの標準機能を使う

Node に ZIP 圧縮の標準APIは無い。外部ライブラリを足さない方針（5.1.4）に対して、配布物を作るためだけに依存を増やすのは筋が悪い。Windows は `Compress-Archive`、その他は `zip` を呼ぶ。どちらも無い環境では、写したディレクトリを残して手順を案内する。

### 5.3 展開後の起動を自動で確かめる

`distribution.spec.js` が組み立てた `アプリ内部（変更しないでください）/` を別ポートで配信し、起動・保存・再読み込み・エクスポート・外部通信なしを通す。開発時ツール（`tools/`、`tests/`、`docs/`、`node_modules/`、`package.json`）が含まれていないことも確かめる。

ZIP そのものの展開は確かめない。`build-dist.mjs` は写したディレクトリをそのまま固めるだけで、展開結果はこのディレクトリと同一である。

### 6.1 `StorageAdapter` の検索3操作は残す（F-28）

`findTaskTemplates` / `findTemplateSeries` / `findProjectGroupByProjectId` は `src/app/` から呼ばれていない。

**決定: 操作は残し、名前の取り違えだけを直す。**

呼ばれない理由は設計から来ている。`persistence.run(plan)` は読み込み済みのデータセットを `plan` へ渡し、読み込みから書き込みまでを1区間にする。ここで索引を引き直すと、その区間の外を読むことになり、検証と書き込みの間に割り込む隙間ができる。**アクション層が受け取った一覧の中だけで判断するのは正しい。**

一方で、`projectActions.js` に同名で配列を取る関数があり、import を取り違えやすかった。こちらを `findLoadedProjectGroup` へ改名し、役割の違いをコメントへ書いた。
