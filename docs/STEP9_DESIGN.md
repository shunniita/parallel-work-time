## 0. 本書の位置づけ

Step 9 の実装で、**仕様が直接には決めていない点**と、**実装が選んだ点**を記録する。仕様の記述をそのまま写すことはしない。

Step 9 の目的は、ブラウザ内だけにある全データを利用者がファイルとして退避・復旧できるようにし、Step 10 の完全削除へ先立って共通の安全経路を確立することである。成功条件は、正しいJSONなら全データを一括で置き換えられ、不正なJSONまたは保存失敗では置換前データが一部も変わらないことである。

Step 3 で定めた `StorageAdapter.exportAll()` / `importAll()` を公開保存契約として使い、Step 6〜8 で確立した「domain が判断し、`app/actions/` が保存を調停し、UI は利用者との対話だけを受け持つ」という分担を踏襲する。

### 1.1 異なるUTCオフセットは「元の壁時計と元の瞬間」を保つ

保存済み区間の編集では、ISO文字列の壁時計部分を入力欄へ表示し、保存時にも元のオフセットを使う。たとえば `2026-08-01T09:00:00Z` は、端末がJSTでも `09:00` と表示され、無変更保存後も `2026-08-01T09:00:00Z` のままである。

この決定は、インポートしたデータを画面で開いただけで工数の基になる瞬間を変えないためである。`Z`、UTCより東側・西側、時刻変更、未終了区間への終了補完を、実行環境のタイムゾーンに依存しない単体テストで固定した。夏時間の地域規則そのものを再現する機能ではないが、少なくとも保存済み値の無変更編集では瞬間を変えない。

## 3. 仕様が決めていない点の決定

### 3.1 エクスポートは保存アダプターの公開契約から作る

画面用のstoreを直接JSON化せず、`StorageAdapter.exportAll({ exportedAt })` から出力を作る。アダプター契約テストで確かめるデータと、実際に利用者が受け取るデータを同じ経路にするためである。

出力は人が確認しやすい2空白インデントと末尾改行を使い、ブラウザの `Blob` と一時URLでダウンロードへ渡す。ファイル名の日時は端末のローカル日時、JSON内の `exportedAt` はオフセット付きISO秒精度とする。

ダウンロードへの引き渡しが成功してから、同じ `exportedAt` を `settings.lastExportedAt` へ保存する。引き渡し前に記録すると、ファイル化に失敗しても「エクスポート済み」に見えるためである。出力JSON内の `settings.lastExportedAt` にも同じ値を入れる。

### 3.2 インポート検証は2段階にする

検証入口は次の2か所に置く。

1. `io/importJson.js` がファイルを読み、JSON構文・構造・業務整合性を確認する。これは全置換の確認を出す前に、利用者へ具体的な原因を返すための早期検証である。
2. `MemoryAdapter.importAll()` と `IndexedDbAdapter.importAll()` が同じ `validateImport()` を再実行する。こちらが不変条件を守る権威ある保存入口であり、UIや別の呼び出し元が早期検証を省いても不正データを保存できない。

同じ検証を重ねるのは重複ではなく、説明責任と保存防御の役割が異なるためである。`validateImport()` は、まず `schema.js` の1レコード単位の構造検証を行い、それが通った場合だけ `integrity.js` の集合をまたぐ検証へ進む。

### 3.3 全置換は「全て成功」か「変更なし」にする

IndexedDBでは、全ストアの `clear()` と `put()` を1つの `readwrite` トランザクションに入れる。途中の要求が失敗した場合はトランザクション全体を巻き戻す。

MemoryAdapterでは、新しい `Map` 群へ全件を複製し終えてから、最後の代入1回で保存集合を切り替える。どちらの実装も、検証と主キーの取り出しを置換開始前に済ませる。

これにより `importAll()` の失敗保証は次の1つになる。

> 取り込みが完了を返さなければ、呼び出し前の全データを保持する。

### 3.4 退避の有無を破壊的操作から分離する

`io/safetyExport.js` の `runDestructiveAction()` は、対象がインポートか削除かを知らない。次の契約だけを持つ。

- 退避ありなら `exportData()` の完了を待ってから破壊的操作を呼ぶ。
- 退避なしなら「取り消せない」ことの確認済みフラグが無い限り、破壊的操作を呼ばない。
- 退避または破壊的操作が失敗した場合は、その例外を呼び出し側へ返す。

Step 9 では全置換インポートから使い、Step 10 では実施回・案件グループ・アーカイブデータの完全削除から同じ関数を呼ぶ。破壊的操作の種類を増やすための抽象化ではなく、仕様9.4が明示する共通退避処理の実装である。

### 3.5 確認UIは既存の2種類を使い分ける

ファイルの事前検証が通った時点で、画面内に「退避して取り込む」「退避せずに進む」「やめる」を表示する。「退避せずに進む」を選んだ場合だけ、既存の `confirmPanel.js` でもう一度、取り消せない旨を確認する。

理由入力は求めないため `reasonConfirm.js` は使わない。理由必須は変更履歴へ残す操作の意味であり、全置換インポートの安全確認とは別の契約だからである。

### 3.6 アーカイブでは転記完了日時を保つ

アーカイブは「転記済みの実施回を通常一覧から分離して保持する状態」である（仕様書4章、7章）。したがって、転記済みからアーカイブへ進むときは既存の `transferredAt` を保持し、同じ遷移で `archivedAt` を記録する。作業中・集計済みへ戻るときだけ、両方を `null` にする。

この状態日時の組み立ては `runStatus.timestampsForStatus()` に置き、`transferActions.changeStatus()` が利用する。Step 10 でアーカイブ遷移を `TRANSITIONS` へ追加した時点から、`integrity.js` の「アーカイブ済みは `transferredAt` と `archivedAt` を持つ」という検証と同じ契約になる。

## 4. インポート時の業務整合性

### 4.1 拒否する状態

構造が正しくても、画面の通常操作から作れず、取り込み後に安全に直せない状態は拒否する。

| 分類 | 拒否する例 |
| ---- | ---------- |
| 識別子 | 最上位レコードまたは入れ子の識別子重複、案件ID重複 |
| テンプレート | 同じ対象種別・バリエーションに有効版が複数、同じ系列内の版番号重複 |
| 参照 | 存在しない案件・テンプレート・作業項目定義を実施回が参照する、参照テンプレートの版が一致しない |
| 区間 | 終了が開始より前である |
| 実施回状態 | 未終了区間、`transferredAt`、`archivedAt` と `status` の組み合わせが許可状態と矛盾する |
| 変更履歴 | `operation` と `entityType` の組み合わせが一致しない |

### 4.2 拒否しない状態

仕様が警告または任意項目として認め、取り込み後に画面から確認・修正できるものは通す。

| 状態 | 理由 |
| ---- | ---- |
| 区間の重複 | 仕様8.9.5は警告にとどめ、保存を許す |
| 累計が総予定数を超える | 仕様8.9.7は警告して続行できる |
| 外部項目コード未設定 | 仕様8.7.4は集計時の警告であり、未設定自体を禁止しない |

変更履歴の `targetId` は現存レコードへの外部キーとして扱わない。削除履歴が指す対象はすでに存在しないことが正常であり、履歴は削除前の要約を保持する監査記録だからである。したがって、変更履歴については `operation` と `entityType` の対応を検査し、`targetId` の現在存在は要求しない。

## 5. 画面遷移と失敗時の扱い

### 5.1 エクスポート

```text
設定・バックアップ画面
  → 全データを StorageAdapter から読み出す
  → JSONをダウンロードへ渡す
  → lastExportedAt を保存する
  → 画面の全データを再読込して成功を表示する
```

ファイル化または設定保存が失敗した場合は画面にエラーを表示し、成功表示へ進まない。

### 5.2 インポート

```text
ファイル選択
  → 読み取り・早期検証
  → 全置換の選択（退避する／退避しない／やめる）
      → 退避する: 現在データをエクスポート
      → 退避しない: 取り消せない旨を再確認
  → 保存入口で再検証
  → 全データを原子的に置換
  → storeを再読込して成功を表示する
```

ファイル選択を取り消した場合、構文・検証エラー、退避の失敗、置換の失敗では、成功表示へ進まない。再選択または取消ができる状態を保ち、入力要素の値そのものをアプリケーション状態の正としない。

## 6. モジュール分割

| ファイル | 責務 |
| -------- | ---- |
| `src/domain/integrity.js` | 取り込み全体の構造検証を束ね、複数レコードにまたがる業務整合性を純関数で検査する |
| `src/app/actions/settingsActions.js` | 設定保存、エクスポート、全置換インポートを調停し、保存後のdatasetを返す |
| `src/io/exportJson.js` | ファイル名、JSON直列化、ブラウザのダウンロード処理を受け持つ |
| `src/io/importJson.js` | `File` の読み取り、JSON構文解析、確認前の早期検証を受け持つ |
| `src/io/safetyExport.js` | 退避の完了または退避なし確認を、破壊的操作の前提条件にする |
| `src/ui/views/settingsView.js` | 設定・バックアップ画面、ファイル選択、二段階確認、結果表示を受け持つ |
| `src/storage/MemoryAdapter.js` | 検証済みデータを新しい保存集合へ組み立て、最後に一括で切り替える |
| `src/storage/IndexedDbAdapter.js` | 検証済みデータを全ストア共通の1トランザクションで置き換える |
| `src/ui/components/dateTimeInput.js` | 編集元のUTCオフセットを保持した日時入力の読出しを受け持つ |
| `src/ui/components/intervalEntryForm.js` | 編集時に元区間のオフセットを日時入力へ渡す |

UIはIndexedDBを直接扱わず、domainは `File`、`Blob`、DOMを参照しない。ブラウザ固有処理は `io/` と `ui/` に閉じ込め、MemoryAdapterとIndexedDbAdapterの公開契約を同じテストで検証する。
