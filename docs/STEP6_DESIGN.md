## 1. 扱うデータ

`TimeInterval`（仕様書6.7）は `TaskRecord.intervals[]` の要素である。

| 項目 | 内容 |
| ---- | ---- |
| `intervalId` | 識別子 |
| `type` | `"work"` \| `"break"` |
| `startAt` | オフセット付きISO 8601（秒精度、8.4.4） |
| `endAt` | 同上。`null` は未終了区間（6.7） |
| `participants` | 文字列配列。作業者マスターは設けない（6.7） |
| `createdAt` / `updatedAt` | 同上 |

WorkRun は `tasks[] → intervals[]` を内包する単一ドキュメントである（計画書§3.3）。区間1件の変更でも WorkRun 1件を書き戻す。この粒度は初版の性能目標に対して十分と判断済みであり、Step 6 で変えない。

## 2. 操作の変換規則

7つの操作すべてを「進行中区間を閉じる」と「新しい区間を開く」の組み合わせとして定義する。`intervalOps.js` はこの表をそのまま関数にする。

| 操作 | 前提状態 | 進行中区間 | 新規区間 | 参加者 |
| ---- | -------- | ---------- | -------- | ------ |
| 開始 | 未着手 / 完了 | — | `work` を `at` から | 入力する |
| 休憩 | 作業中 | `endAt = at` | `break` を `at` から | 直前の `work` から引き継ぐ（8.9 末尾） |
| 再開 | 休憩中 | `endAt = at` | `work` を `at` から | 直前の `break` から引き継ぐ |
| 終了 | 作業中 / 休憩中 | `endAt = at` | 作らない | — |
| 参加者変更 | 作業中 / 休憩中 | `endAt = at` | **同じ `type`** を `at` から（8.4.10 補足2） | 新しい一覧を入力する |
| 区間追加 | 任意 | 触らない | `type` / `startAt` / `endAt` を指定（8.4.11） | 入力する |
| 区間編集 | 任意 | 触らない | 既存区間の `startAt` / `endAt` / `type` / `participants` を差し替え（8.4.5） | 入力する |

`at` の初期値はすべて現在日時（8.4.3）。`activeInterval()`（`taskState.js` に実装済み）が「進行中区間」を返す。

### 2.1 参加者の引き継ぎで生じる隙間

「休憩」は直前の作業区間の参加者を引き継ぐ、と仕様書8.9 末尾が定めている。「再開」については明文がないが、対称に直前の `break` から引き継ぐのが自然である。

ただし `break` は参加者0人を許す一方、`work` は0人を禁止する（8.9.4）。**0人の休憩区間から再開すると、引き継いだ結果が 8.9.4 違反になる。**

決定: 再開時、引き継いだ参加者が0人なら**参加者の入力を求める**。黙って0人の `work` を作らない。`intervalOps.resume()` は0人を渡された場合に検証エラーを返し、UI 側が参加者入力を開いてから呼び直す。

### 2.2 手動追加は未終了にできない

補足1 は「**ボタン操作によって生じる**未終了区間は作業項目ごとに一つまで」と限定している。手動追加（8.4.11）と編集（8.4.5）については重複を許すとだけ書かれており、未終了にできるかは書かれていない。

決定: **手動追加は `endAt` を必須とする。** 未終了の区間を任意個作れると `activeInterval()` が「開始が最も新しいもの」という便宜的な規則でしか進行中を決められなくなり、ボタン操作の前提（進行中は高々1つ）が崩れる。手動追加は「後からの実績修正」（8.4.11）が目的なので、終了時刻が分かっている場合しか使わない。

同じ理由で、**編集で `endAt` を `null` へ戻すことはできない**。8.8.4 が求めるのは `null` → 値の補完であり、逆方向の必要性はない。もともと未終了の区間を編集する場合に限り、`endAt` を空のまま保存できる。

### 2.3 進行中区間の個数の担保

「ボタン操作で生じる未終了区間は項目ごとに1つまで」（補足1、A-17）は、次の2点で成立させる。

1. 開始は 未着手 / 完了 の状態でのみ有効（`taskState.js` の `OPERATIONS_BY_STATE` に実装済み）。作業中・休憩中には開始ボタンを出さない。
2. `intervalOps` の各関数が、前提状態と合わない入力に対して必ず失敗する。UI のボタン制御だけに頼らない。

複数の作業項目を同時に作業中にできる（8.4.9、A-16）ことは制約しない。上限は作業項目ごとである。

## 3. 検証と警告の切り分け

Step 5 で「拒否は `errors`、確認して続行できるものは `warnings`」という区別を作った。Step 6 でも同じ形に従う。

| 内容 | 扱い | 根拠 |
| ---- | ---- | ---- |
| `endAt` が `startAt` より前 | 拒否 | 8.9.3（同一日時は0秒として許可） |
| `work` の参加者が0人 | 拒否 | 8.9.4 |
| `break` の参加者が0人 | 許可 | 8.9.4 |
| 同一作業項目内の区間重複 | 警告のみ | 8.9.5、補足1（別グループの同時並行を表現できるようにするため） |
| 参加者名の表記ゆれ | 何もしない | 8.9.9（利用者の判断に委ねる） |
| 未終了区間がある実施回の集計済み化 | 拒否 | 8.9.6（Step 8 の範囲） |

区間重複の検出は `overlap.js` に実装済み（`findOverlappingPairs`）。接触（前の終了＝次の開始）を重複としない判断も入っている。休憩と参加者変更は同時刻で区間を継ぐため、これは必須の挙動である。

### 3.1 warnings の形式（D-15 の先行適用）

レビュー指摘 D-15 は「`warnings.length > 0` を無条件に累計超過とみなす作りは、別種の警告を足した瞬間に誤爆する」と指摘している。推奨対応時期は Step 7 前だが、**Step 6 で新設する検証関数は最初から種別コードを持つ形にする。**

```js
{ code: 'intervalOverlap', path: '作業区間', message: '…' }
```

既存の `validateRunDraft` を同じ形へ揃えるのは D-15 の対応時（Step 7 前）に行う。Step 6 で新旧2形式が併存するが、区間の検証と数量の検証は呼び出し経路が分かれているため衝突しない。

### 4.1 既存の規約への接続

先の修正で入れた3つの規約に、Step 6 の新規コードをそのまま乗せる。

- **保存経路**（`persistence.js`）: `intervalActions` は `persistence.run(plan)` を使う。`plan` の中で `loadAll()` の結果を受け取り、検証・組み立て・書き込みを1区間で行う。アクション側で `loadAll()` を呼ばない。同一 WorkRun への連続書き込み（「項目Aで開始 → 項目Bで開始」）が常態になるのが Step 6 であり、この直列化は Step 6 のためにある。
- **状態ガード**（`runStatus.js`）: 区間を書き換えるアクションはすべて `isRunEditable()` を通す。転記済み・アーカイブの実施回では記録できない（7.2）。
- **再描画**（`store.js`）: 区間の追加・削除は構造が変わるので `setState`。時刻入力欄への打ち込みでは再描画しない。

### 4.2 F-25（`datetime.js`）で足すもの

レビュー指摘 F-25 のとおり、Step 6 に必要な API をここで揃える。

| 追加 | 用途 |
| ---- | ---- |
| `fromDateTimeLocal(value, offsetMinutes)` | `<input type="datetime-local">` の値 → オフセット付きISO |
| `toDateTimeLocal(iso)` | ISO → `datetime-local` の値（秒まで） |
| `compareIso(a, b)` | 大小比較。各所へ `parseIso` の数値比較が散らばる前に集約する |
| `addSeconds(iso, seconds)` | 秒の加減算 |

あわせて符号規約を統一する。現在 `formatOffset()` は `getTimezoneOffset()` 規約（西が正）、内部の `parseOffsetMinutes()` は ISO 規約（東が正）で、同一モジュール内で逆になっている。

決定: **公開 API は ISO 規約（東が正）へ統一する。** `Date#getTimezoneOffset()` の値を扱うのは `toIsoSecond()` の内部だけにし、そこで反転する。`formatOffset()` の引数の意味が変わる破壊的変更なので、単体テストもあわせて直す。

### 4.3 B-6（`renderDetail` のルーティング）

`taskDetailView` を足すのは PR-B である。この時点で `main.js` の if 連鎖を `VIEW → {render, reset}` の登録テーブルと、案件画面内サブルート（project / run / task）の2段構成へ分割する。未知ビューが `projectView.render()` へ落ちる既定も、明示的なプレースホルダへ改める。

8.8 の「しきい値超過の1分ごと再評価」は計画書では Step 11（横断要件）である。Step 6 では次までにとどめる。

## 6. 未決事項

実装に入る前、または実装中に決める必要がある。

### 6.1 区間削除と変更履歴の順序（要判断）

計画書 Step 6 に「区間編集・削除」が入っている一方、変更履歴（`changeHistory`、`reason` 必須）は Step 10 である。仕様書11章は「作業区間または直接入力の削除」を履歴の記録対象と定めており、`schema.js` の `validateHistoryEntry` も `reason` を必須にしている。

**このまま実装すると、Step 6〜9 のあいだ「履歴を残さずに区間を削除できる」期間が生まれる。** 選択肢は3つ。

| 案 | 内容 | 評価 |
| -- | ---- | ---- |
| A | Step 6 では削除を実装せず Step 10 へ回す | 編集だけでも実績修正はできる。範囲が小さい |
| B | Step 6 で削除＋履歴記録を実装する | 履歴の書き込み経路を先取りする。理由入力のUIが要る |
| C | Step 6 で削除だけ実装し、履歴は Step 10 で後付け | 記録欠落の穴が数 Step 残る。採らない |

推奨は **B**。`changeHistory` のスキーマと検証は既にあり、足すのは「削除時に理由を入力させて1件書き込む」だけである。削除を実装しておかないと、手動追加を誤った場合に取り消せない。

### 6.2 参加者候補の収集範囲（要判断）

8.4.7 は「過去に入力した参加者名を候補表示する。候補は過去データから抽出する」とだけ定める。計画書§ は「全 `participants[]` からの一意集合」としている。

全データを走査すると、区間2,000件の性能目標（13章）でも毎回の候補生成が無駄に重い。実用上は「同じ実施回 → 同じ案件 → 全体」の順に並べると選びやすい。

推奨: 収集は全データから行い（`participants.js` の純関数）、**並び順を「当該実施回での出現 → それ以外」とする**。件数が問題になるまで絞り込みはしない。

### 6.3 日跨ぎ区間の表示（判断は UI 実装時）

8.4.8 の日跨ぎは、オフセット付き ISO で保存しているため計算上は何もしなくてよい。区間履歴の表示で終了時刻が翌日以降になる場合に日付を併記するかは、`taskDetailView` を書くときに決める。
