## 1. 指摘

### FB-1 区間履歴の並べ替えが辞書順比較で、オフセット混在時に実時刻順にならない

- 重要度: **Minor**（現アプリが書くデータでは実害なし。規約との不整合が主）
- 対象: `src/ui/views/taskDetailView.js:245-248`

```js
const ordered = [...task.intervals].sort((left, right) =>
  left.startAt < right.startAt ? -1 : left.startAt > right.startAt ? 1 : 0,
);
```

ISO 文字列の辞書順比較である。オフセットが揃っているうちは実時刻順と一致するが、混在すると崩れる。例:

- `2026-08-01T23:00:00-05:00`（= 8/2 04:00Z）
- `2026-08-02T00:00:00+09:00`（= 8/1 15:00Z）

辞書順は前者が先だが、実時刻は後者が9時間早い。本アプリの記録経路は常にローカルオフセットで書くため揃うが、インポートJSON（仕様書9.3）は `Z` を含む任意のオフセットを許しており（`isValidIsoSecond`）、取り込んだデータで並びが狂いうる。

F-25 の対応で「`parseIso` の数値比較が散らばる前に `compareIso` へ集約する」と決めた（PWT-REVIEW-001）。その直後に集約先を使わない比較が1か所入った形であり、`compareIso(left.startAt, right.startAt)` へ差し替えるのが一貫する。

- 推奨対応時期: PR-B2 のついで（`taskDetailView` を再度触るため）

### FB-2 閲覧のみへ変わった実施回で、開きかけの操作フォームが残って描かれる

- 重要度: **Minor**（保存はアクション層の `isRunEditable()` が拒否するため、記録は守られる）
- 対象: `src/ui/views/runView.js:299-301`、`src/ui/views/taskDetailView.js:395`

`renderTaskBody()` は `local.operation` が対象の作業項目と一致すればフォーム行を描き、実施回が編集可能かを見ない。`taskDetailView` も `renderOperationForm(task)` を編集可否と無関係に呼ぶ。フォームを開いたまま実施回が転記済みへ変わってデータセットが更新されると、「閲覧のみ」の注記と入力フォームが同じ画面に同居する。確定を押せば `RunNotEditableError` がフォーム内に出るので誤記録にはならないが、表示として矛盾する。

現状この状況を作るには多重タブか手動のデータ書き換えが要る。ただし **Step 10 で状態遷移の操作（転記済み化・アーカイブ）が画面に入ると、同一画面内の操作で到達できるようになる**。`render()` 冒頭の「対象の作業項目が消えたら閉じる」（`runView.js:323-329`）と同列に、`!isRunEditable(run)` でも `local.operation = null` とする1行で閉じられる。

- 推奨対応時期: Step 10 前

### FB-3 `dateTimeInput.read()` にオフセットを渡す口が無い（B2 の区間編集で決めが要る）

- 重要度: **Note**（現状の記録経路では問題にならない。B2 への引き継ぎ事項）
- 対象: `src/ui/components/dateTimeInput.js:72`、設計メモ §4.2.1

`read()` は常に `fromDateTimeLocal(input.value)` とオフセット省略で呼ぶ（入力日のローカルオフセット）。一方、設計メモ §4.2.1 は「既存の区間を編集する場合はその区間のオフセット（`offsetMinutesOf`）で書き戻す」と書いており、部品にはそれを渡す手段が無い。B2 の区間編集を作るときにどちらかへ決める必要がある。

1. **部品はこのままにし、編集も入力日ローカルで統一する（推奨）**。夏時間非対応（日本前提）の決定下では、日本のデータのオフセットは常に `+09:00` ＝ローカルと一致し、区別に意味が無い。§4.2.1 の該当文を「試験用の明示のみ」へ改める。
2. `read()` に `offsetMinutes` オプションを足し、編集時だけ元区間の値を渡す。インポートした異オフセット区間の編集で元の表記が保たれるが、契約が2本になる。

案1のほうが、SOL-1 で立てた「オフセットは `fromDateTimeLocal` に決めさせる」という単純な契約を保てる。異オフセット区間を編集した場合に表記がローカルへ変わるが、指す瞬間は変わらない。

- 推奨対応時期: PR-B2 の区間編集の実装時

### FB-4 バッジ種別の判定が文字列直書き

- 重要度: Nit
- 対象: `src/ui/views/taskDetailView.js:211`

`interval.type === 'break'` と直書きしている。同ファイルは `effort.js` から import 済みであり、`INTERVAL_TYPE.BREAK` を使えば `'break'` の正が一重になる。区間種別の値が変わることはまず無いが、リポジトリ全体では定数参照で統一されており、ここだけ浮いている。

### FB-5 再開の説明文が「休憩そのものが無い」場合と区別できない

- 重要度: Nit（到達には多重タブ級の状態ずれが要る）
- 対象: `src/ui/components/intervalOperationForm.js` の `describeOperation`

`RESUME` で `activeInterval` が null のとき `inherited` は空配列になり、「直前の休憩は参加者0人です」と出る。実際は進行中の休憩が存在しない状態であり、文言が事実と合わない。確定すれば domain 層が状態エラーで拒否するので実害は無いが、フォームを開く前提（休憩中）と説明文の前提が独立している点は覚えておいてよい。

### FB-6 汎用の日時表示整形が `history.js` に同居している

- 重要度: Note（配置の問題。動作には影響しない）
- 対象: `src/domain/history.js` の `formatIsoForHuman` / `formatIntervalRange`、`src/ui/views/taskDetailView.js:20` の import

`history.js` の表明された責務は「簡易変更履歴の組み立て」だが、`formatIsoForHuman` は汎用の日時表示整形であり、`taskDetailView` が区間履歴の表のためにここから import している。UI が「履歴」モジュールに依存する形は、読み手に「区間履歴＝変更履歴？」という誤読の芽を与える。D-16 の寄せ先整理（Step 8 前）のとき、表示整形は `src/ui/labels.js` か datetime 隣接の表示層へ移すときれいになる。

## 2. 良かった点（変更不要）

1. **A-17 の担保が2層で成立している。** UI はボタンの非表示・無効で、domain は `intervalOps` の前提状態検査で、それぞれ独立に「未終了区間は項目ごとに1つ」を守る。E2E T-17 が両方（行にボタンが出ない・詳細で無効・区間が増えない）を見ている。
2. **SOL-1 の契約が UI 側で守られている。** `fromDateTimeLocal` へオフセットを渡す呼び出しは `src/ui/` にゼロで、「オフセットは domain に決めさせる」が実際に貫かれている。
3. **保存中の再描画競合の扱いが記録に残っている。** フォームが閉じない不具合を E2E で検出し、修正し、単体テスト（「保存の途中で再描画が走ってもフォームを閉じる」）で固定した経緯がコミットとテスト名から追える。再描画の規約（`store.js`）の実例として価値がある。
4. **B-6 の登録表が意図どおり効いている。** 未知ビューが案件詳細へ落ちず、未実装画面・未実装操作の両方が「理由つきで無効」という同じ扱いで統一されている。
5. **`data-testid` の語彙が一貫している。** `op-*` / `row-op-*` / `interval-*` / `summary-*` と層ごとに接頭辞が分かれ、E2E と単体テストが同じ語彙で書けている。
