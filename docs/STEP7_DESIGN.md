## 2. 直接入力と作業区間の違い

| 観点 | 作業区間（8.4） | 直接入力（8.5） |
| ---- | --------------- | --------------- |
| 時刻 | 開始・終了を持つ | 持たない。秒数そのもの |
| 参加者数 | 工数へ掛ける（8.6.1） | **掛けない**（8.5.6、8.6.6） |
| 参加者0人 | `work` は禁止（8.9.4） | 許す（§3.2） |
| 作業項目の状態 | 操作ごとに前提がある（12.4） | 全状態で足せる（12.4） |
| 重複 | 時間帯の重なりを警告（8.9.5） | 同一参加者・同一秒数を警告（8.9.8） |
| 備考 | 無し | **必須**（8.5.4） |

`participants` の意味も違う。区間では工数の乗数だが、直接入力では「誰の分か」を後から照合するための補助情報にすぎない（6.8）。`seconds` は既に人数を含んだ総工数である。

この取り違えは工数が人数倍ずれる形で効くため、入力欄の見出しを「時間」にせず「追加工数」とし、注記に「参加人数を含んだ総工数（人×時間）」と明記する（8.5 補足の要求）。

## 3. 仕様が決めていない点の決定

### 3.1 0秒の直接入力を拒否する

仕様書8.5.5 が明記するのは負値の禁止だけである。0秒については何も言っていない。

**決定: 0秒を新しく作ることは拒否する。インポート検証（`schema.js`）は0秒を通したままにする。**

0分0秒の直接入力は工数を1秒も足さず、備考だけが残る。分・秒の入力漏れである可能性が高く、記録として意味を持たない。一方、読み込みは既存データを受け入れる側であり、書き込みより緩くてよい（9.3 は `schemaVersion` の一致だけを取り込みの条件としている）。両者で基準が違うのは意図したものである。

拒否の判断は `directEntryOps.js` が持ち、画面の `durationInput.js` は「分・秒それぞれが0以上の整数として読めるか」だけを見る。同じ規則を2箇所へ書かない。

#### 編集では「もともと0秒」を通す（レビュー指摘 S7-2）

本書 1.0 の決定は「新規入力・**編集**では0秒を拒否する」であった。これには穴があった。編集はレコード全体を検証するため、取り込んだ0秒レコードは備考や参加者だけを直す場合でも保存できない。「取り込めるが直せない」レコードが生じ、インポートを緩くした意味が失われる。

**決定を次へ改める。**

| 場面 | 0秒の扱い |
| ---- | --------- |
| 新規追加 | 拒否 |
| 編集（もとが1秒以上） | 拒否。0秒へは変えられない |
| 編集（もとが0秒、0秒のまま） | **許可**。備考・参加者だけを直せる |
| 編集（もとが0秒、1秒以上へ） | 許可 |
| インポート検証 | 許可（変更なし） |

判定は `checkSeconds(problems, seconds, {allowZero})` の `allowZero` で表す。`editDirectEntry` が `current.seconds === 0` のときだけ立てる。編集フォームは分・秒を常に送り返すため、「秒数を変更していない場合」ではなく「もとが0秒である場合」を条件にする必要がある。

### 3.2 参加者0人を許す

`work` 区間が0人を禁じられているのは（8.9.4）、参加者数が工数の乗数だからである。0人だと工数が0になり、記録として成立しない。

直接入力にはこの理由が無い。`seconds` は既に人数を含んだ値であり、参加者は照合用の補助情報である。誰の分か分からない計測漏れを、備考だけ添えて足せる必要がある。

**決定: 直接入力の参加者は0人でよい。** 一覧では「なし」と表示する。

### 3.3 重複候補の判定条件

仕様書8.9.8 は「同一作業項目、同一参加者、同一秒数」とだけ書く。実装が決めた点は次の3つである。

| 論点 | 決定 | 理由 |
| ---- | ---- | ---- |
| 参加者の並び順 | 問わない（集合として比較） | 「甲、乙」と「乙、甲」は同じ顔ぶれである。入力した順で判定が変わるのは利用者から見て理解できない |
| 備考 | 比べない | 同じ工数を二度登録したとき、備考の書き方まで一致するとは限らない。一致を要求すると警告が出なくなる |
| 編集時の自分自身 | 除く | 値を変えずに保存し直しただけで警告が出ると、利用者は消しようのない警告を見続けることになる |

判定は同一作業項目の中だけで行う。別の作業項目に同じ工数があっても警告しない。

警告であって拒否ではない。別の日に偶然同じ工数を足すことはあり、そのたびに確認を挟むと通常の入力が滞る。保存したうえで返し、画面が警告領域へ出す（区間の重複と同じ扱い）。

### 3.4 直接入力の編集・削除を「履歴編集」に載せない（仕様書1.2 で確定）

区間履歴の編集・削除は「履歴編集」トグルの内側にある。直接入力も同じ場所へ寄せるのが自然に見えるが、そうしなかった。

**理由**: 仕様書12.4 の対応表で「履歴編集」は**未着手では無効**である。一方、直接入力は**全状態で追加できる**。したがって「区間は1件も無いが直接入力だけある作業項目」が普通に生じ、そこではトグルを押せないため編集も削除もできなくなる。

**決定: 直接入力の編集・削除ボタンは、実施回が書き換えられる限り常に出す。**

削除は理由必須の確認を経るので、常時表示でも誤操作にはつながらない。

#### 本項の当初の記述の誤り（レビュー指摘 S7-1）

本書 1.0 は、この決定の根拠を「12.4 は直接入力の編集・削除について何も定めていないため、この選択は仕様に反しない」と説明していた。**これは誤りである。** 仕様書1.1 の12.4 処理表は「履歴編集 ｜ 既存の区間**および直接入力**を修正・削除する」と定めており、実装はこれに反していた。

実際には、仕様書1.1 の12.4 が内部で矛盾していた。処理表は履歴編集へ直接入力を含める一方、状態表は未着手で履歴編集を無効にしており、両方を満たす実装は存在しない。

この矛盾は**仕様書1.2 で解消した**。「履歴編集」の対象を作業区間のみとし、直接入力の修正・削除を独立した常時操作として明記した。現在の実装は仕様書1.2 に適合している。

### 3.5 実施回詳細の行には出さない

区間の開始・休憩・再開・終了は実施回詳細の作業項目行からも押せる（PWT-DESIGN-006 §4.4）。直接入力は作業項目詳細だけに置く。

備考が必須で入力項目が多く、行の中へ収まらない。実施回詳細の行には「直接入力の追加・編集・削除は作業項目詳細から行う」旨の注記を置く。

### 3.6 直接入力一覧は並べ替えない

区間は開始時刻を持つため時刻順に並べる（レビュー指摘 FB-1）。直接入力には順序を決める値が無い。`createdAt` で並べることもできるが、登録した順とほぼ同じであり、わざわざ比較する意味が無い。

**決定: 保存されている順（＝登録順）でそのまま出す。**

### 4.1 参加者の比較キーに区切り文字を使わない（レビュー指摘 S7-3）

重複候補の判定（§3.3）は参加者一覧を1つの文字列へ直して比べる。この連結に単純な区切り文字を使ってはならない。参加者名は自由入力であり（6.7）、区切りに選んだ文字は名前の中にも現れうる。空白区切りなら `['甲 太郎']` と `['甲', '太郎']` が同じキーになり、別の顔ぶれを重複候補として警告してしまう。

`JSON.stringify([...participants].sort())` を使う。要素の境界を引用符で表すため、この取り違えが起きない。

制御文字を区切りに使う手もあるが、採らない。実装当初はここに NUL バイトが入っており、次の2つが同時に起きていた。

- ソースの上で空白と見分けが付かない。エディタでも `cat` でも読めない。
- NUL を含むファイルを Git がバイナリと判定し、`git diff` が中核ドメインロジックの差分を出さなくなる。

再発を機械的に防ぐため、`tests/unit/sourceHygiene.test.js` で `index.html` と `src/` 配下に制御文字が無いことを検査する。

### 4.2 共通化した2つ

**`taskTarget.js`**: 区間と直接入力は「実施回と作業項目を引く → 状態ガードを通す → 配下の配列を差し替えて WorkRun を書き戻す」という同じ形をとる。差は差し替える配列だけなので、その手前を集約した。`intervalActions.js` の `findTask` / `locateTask` / `assertEditable` / `replaceIntervals` はここへ移した。

**`deleteConfirm.js`**: 削除確認は理由必須・確定・取消・削除できない場合の表示という作りが同じで、違うのは見出しの語だけである。`subject` で受け取る形にし、区間（`'区間'`）と直接入力（`'直接入力'`）で共有する。テスト用の `data-testid` は変えていない。

## 5. 変更履歴（11章）

直接入力の削除は変更履歴の記録対象である（11章の「作業区間または直接入力の削除」）。区間削除（PWT-DESIGN-006 §6.1 の案B）と同じ形にした。

- 削除後の実施回と履歴1件を `saveEntities` で**同一トランザクション**へまとめる。`saveEntity` を2回呼ぶと、間で失敗したときに「記録だけ消えて履歴が無い」または「履歴だけあって記録が残る」状態になる。どちらも後から機械的に直せない。
- `reason` は必須。未入力・空白のみは拒否する。
- 確認画面に出す説明と履歴の要約を同じ関数（`describeDirectEntry`）から作る。「確認した内容」と「履歴に残る内容」が食い違わない。

要約には備考を含める。直接入力は計測の裏づけが無い数字であり、何のために足した分が消えたのかは備考にしか残っていない。
